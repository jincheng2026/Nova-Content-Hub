# 内置资源批量读取与根替换锁保护

日期：2026-10-19。上一目标轮是实际进展：0.3.18前台队列源码`ae3f186`及包已完成；本轮用户保存退出后，实际安装、双宿主官方更新与发行记录`87e7be8`完成，标签`v0.3.18-preview-mac-arm64`指向冻结发行版。下述是该标签之后的独立源码批次，尚未打包或安装，不混入0.3.18的验收声明。

## 从测量到原因

59的安装副本探针显示已有库打开约5.5秒，其中seed约3.9秒。按diagnosing-bugs先建可判红的循环，再依次核对重复恢复、重复资产读取、源文件校验三项预测。`seed-performance-probe.mjs`只操作显式提供库的新副本，比较前后完整快照；故障hook统计真实锁获取，文件读取也按实际fd对应路径分类。

20模板/52提示词的已准备示例库复装使用269次锁与recover，约3,631ms；227次包内读取、585次库内资产读取。此样本的90次锁界限明确失败，它只是此固定fixture的诊断界限，不是产品容量限制。最早探针忘记设置NODE_ENV=test而被拒绝；第一次分类没有跟踪fd，分组错误，日志保留，正确计数以categorized收据为准。

## 最小实现及保护边界

Astra high只读设计、随后检查真实diff；Sol high唯一实施两个生产模块及相关测试。主线程独立审查调用面、重新测量及验证。

- `library()`闭包增加Node内部`readAssetDescriptors`：先验证数组及所有hash（含稀疏项），去重，一次既有锁内完整读取/校验每项，只返回hash/bytes/type，不返回或保留Buffer。
- 只在单项`readAssetInternal`内捕获CORRUPT，继续既有导入校验；身份、恢复、BUSY、不确定锁、unsafe path和I/O错误仍抛出。损坏同hash资产不被覆盖修补。
- 返回前复核root inode与descriptor library ID，再复核root；不把批量过程中得到的旧身份作为当前库授权。
- seed等全部原始及同事资源预检结束后才调用批量API。逐模板`normalizePackage`和`templatePackage`两次资产复验不变；无持久缓存、安装标记跳检、额外IPC或renderer权限。
- 同时复现既有锁清理问题：`locked`未把根身份回调传入`acquire`。在owner写入及release阶段替换为同ID克隆时，旧实现会删掉克隆里的锁。现仅复用既有第四参数保护获取、回收及释放；保留主错误和已提交结果标识。该修复针对当前业务handle，未声称所有历史无pin升级入口都有相同身份保护。

用户提示词编辑、回收站、历史模板包、同版本冲突、导入后hash对比、批量返回后再次篡改/换根均保持原有语义。

## 验证与实际差异

核心文件库417项全部通过；资源目录3项通过，两端类型通过。主线程独立跑批量/根身份17项及完整seed集成11项全部通过。将原0.3.18核心复制到隔离目录再跑四个根替换回归，四项均准确失败；当前代码通过。没有重跑整个仓库verify。

固定副本的锁从269次变为75次；包内读取仍227次、库内资产读取仍585次，确认不是去掉字节验证换速度。两次后继Node样本约1,277ms及2,813ms，机器并非专用性能机，不能按一次耗时承诺固定收益。完整副本和源库快照均不变。
