## 日期规则

处理相对日期时，优先使用系统当前日期换算成绝对日期；如果拿不到系统日期，就保留原文相对说法并标待确认。

规则：

- 用户说「今天」「明天」「下周三」：能换算就写具体日期，同时在 `上下文` 保留原说法。
- 用户说「本周」「本月」「近期」：不要硬编某一天；写入 `计划窗口`，`计划日期` 留空或标待确认。
- 用户说「不急」「以后」「有空」：状态可为 `暂缓` 或 `待确认`，不要塞进今天。
- 用户说「截止」「必须」「交付前」：这才填 `截止日期`。

## 未完成滚动规则

只有用户明确开启自动顺延后，才每天把此前有计划日、仍可执行且未完成的任务顺延到今天，不再等待逐条人工确认。

自动顺延只改变作战日期和来源分组，不代表任务已经完成、仍然重要或今天必须全部做完；当天仍可再做优先级筛选。

### 未完成任务不消失

- 任务只要不是 `已完成`，就必须持续出现在不带日期限制的永久未完成视图。
- 永久视图只按 `进展状态不是已完成` 过滤；禁止再叠加 `计划日是今天/昨天` 之类会随日期失效的条件。
- `今天要做`、`昨日未办` 都只是临时作战视图，不能作为找回任务的唯一入口；任务离开这些视图不等于被删除。
- 每天 11:00 自动扫描 `计划日 < 今天` 且 `进展状态 != 已完成` 的记录；日规划或新增今日任务前也执行同一扫描。
- 自动顺延范围：一次性交付、每日动作和仍需继续处理的时点任务。
- 自动跳过：`进展状态=已完成`、`进展状态=等待外部`、`未办处理=取消`，以及没有计划日的待排期任务。
- 顺延前先保留时间来源：若 `原计划日` 为空，写入本次顺延前的 `计划日`；若已有值则保留，禁止后续连续顺延覆盖最初进入计划的日期。
- 顺延时再统一设置：`计划日=今天`、`计划周期=今日`、`未办处理=顺延今日`、`任务来源=之前项目`。
- 保留原任务名、下一动作、停手线、完成定义、执行策略、资料和责任人，不因顺延擅自重写业务内容。
- 时点任务原时间已经过去时，保留任务并在 `AI判断` 标明「原时点已过，今天需重新确认时点」；不得擅自改截止时间。
- 顺延后必须按记录 ID 或同范围查询回读；只有目标记录日期均为今天且无遗漏，才可报告成功。

### 滚动纪律

- 自动顺延不创建重复记录，只更新既有记录。
- 自动顺延不改成 `已完成`，不删除任务，不改变真实截止时间。
- 已跨日的 `今日新增` 顺延后改为 `之前项目`，保持今日新增与历史迁入分组可见。
- 历史迁入视图可按 `原计划日` 降序分组；原计划日用于识别任务积压时间，不等于真实截止时间。
- 顺延后扫描同类项：目标、最终交付物和下一动作实质相同，或本来就是同一最终交付物的连续步骤时，合并为一条可验收闭环。保留 `原计划日` 最近的记录；同日优先保留 `进行中` 且字段更完整的记录。
- 合并前先把被合并记录里的下一动作、完成定义、停手线、资料和有效判断补到保留记录；保留记录回读成功后，才删除冗余记录，并在 `AI判断` 留下合并说明。只是主题相近、责任人不同、时点不同或交付物不同的任务不得硬合并。
- 等待外部任务保留等待状态和原日期；条件满足后再恢复自动顺延。
- 连续顺延 2 次以上可以触发滞留警报，但警报不能阻止本次顺延。

## 颗粒度规则

默认颗粒度是「能推动一次下一步动作」。

好的：

```text
事项：梳理知识库搭建流程
下一步动作：列出从需求访谈到交付验收的步骤清单
```

太粗：

```text
事项：知识库
下一步动作：推进
```

太细：

```text
事项：打开文档
下一步动作：输入标题
```

长文本超过 12 条候选任务时，先按主题分组，并标出高置信任务；低置信任务放在「可能任务」里等用户确认。不要一次性塞满飞书。

## 例子

输入：

```text
今天整理社区花园的工具清单，下午买种子。本月还要做花坛标识牌，但今天不急。
```

好的候选输出：

```text
我先不入库，先给你候选任务确认：

1. 【社区花园】
   事项：整理工具清单
   下一步动作：盘点现有工具并标出缺口
   计划日期：今天
   原文依据：「整理社区花园的工具清单」
   AI 推断 / 待确认：下一步动作是 AI 拆解
   置信度：高

2. 【社区花园】
   事项：购买种子
   下一步动作：按清单购买当季种子
   计划日期：今天
   原文依据：「下午买种子」
   AI 推断 / 待确认：无
   置信度：高

3. 【社区花园】
   事项：完成花坛标识牌
   下一步动作：确定尺寸和文字
   计划日期：
   计划窗口：本月
   原文依据：「本月还要做花坛标识牌，但今天不急」
   AI 推断 / 待确认：主题为 AI 推断；计划日期待确认
   置信度：中
```

差的候选输出：

```text
3. 【社区花园】
   事项：今晚完成 20 块标识牌并安装
   下一步动作：立即购买材料
```

诊断：原文只说「本月要做，但今天不急」，没有说 20 块、今晚或立即购买。

## 边界处理

### 用户给的内容太模糊

如果无法判断是不是任务，输出「可能任务」而不是硬入库：

```text
这条我不确定是否要入库：
- 原文：____
- 我猜可能是：____
- 不确定点：____

要不要把它作为任务？可以回「要 / 不要 / 改成____」。
```

### 用户要求直接写入

用户最初就明确说「加入计划」「记录到飞书」「写入飞书」，且任务内容无歧义时，这句话本身算唯一一次确认，直接进入飞书写入协议，不再先问候选确认或写入确认。

如果用户只是口喷任务、没有明确要求记录或写入，则先输出候选任务，只请求一次确认。用户回复「确认」后自动执行飞书写入协议，不能跳过 schema、字段映射、去重和 dry-run，也不能再问「确认写入吗」。

### 内容含敏感信息

如果原文包含身份证号、手机号、合同金额、账号密码、医疗/法律/财务高风险信息，不要默认存完整原文。先问：

```text
这段里有敏感信息。要不要只保存摘要和任务，不保存完整原文证据？
```

### 多个目标混在一起

先按主题拆组，不要把所有内容压成一个任务。

### 和日规划类 Skill 冲突

如果用户要的是「今天做什么」「帮我排优先级」「分诊」，停止本 Skill，建议使用日规划类 Skill 或普通对话。

## 自检清单

每次输出候选任务前自查：

- 每条候选都有 `事项` 和 `下一步动作`
- 每条候选都有 `原文依据`
- AI 推断的主题、日期、优先级已经标在 `AI 推断 / 待确认`
- 没有把「本周/本月/近期」硬编成具体日期
- 没有把纯背景提成任务
- 没有把想法、资料、项目状态、业务决策或长期规则写成任务
- 混合输入中的非任务内容已经单独列出建议去向
- 没有在用户确认前输出最终入库表

每次输出入库清单前自查：

- 用户已经确认保留哪些任务
- 默认使用最小入库字段集
- 日常可见字段不超过 6 个
- 后台字段为空时不硬填
- `截止日期` 只来自真实 deadline
- 低置信任务没有被当成确定任务

每次真实写入飞书前自查：

- 已读真实 Base schema
- 已完成字段映射
- 已检查疑似重复
- 已输出 dry-run
- 用户已完成唯一一次确认，或最初的明确写入指令已构成确认
- 未再次请求例行写入确认
- 写入后会读取记录验证并返回 record_id
