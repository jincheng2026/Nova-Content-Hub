# 模板学习、还原与人工验收实施方案

2026-10-18。依据当前源码与 [20-功能收口缺口](20-功能收口缺口.md)、[21-桌面功能批次实现记录](21-桌面功能批次实现记录.md) 定点阅读形成。本文是待实现方案，不是实现或验收报告。遵循功能优先安排：本轮不运行测试、类型检查、构建、探针、应用或助手生成。必要验证代码随功能准备，统一执行留待功能收口。

## 最小完整路径

用户导入参考组 → 在模板页点击“学习并还原” → 使用全局所选助手，固定模板版本和全部参考图 → 助手读取、认领、提交规则证据与还原图 → 模板页对照原图、规则和还原图人工确认 → 同一事务登记已验收新版本 → 使用此版本进入已有内容封面生成流程。

一期学习和还原属于一个固定请求、一次尝试的一组结果。不另建学习调度器、不隐式创建内容、不把模板任务塞进 `content.coverJobs`。这避免污染内容页、日历、发布提醒和内容回收站。仍保留已有“手动导入规则后直接使用”的路径，但只能显示“尚未完成学习验收”。

## 源码事实与存储决策

当前 `file-library/index.mjs` 已有 `template` 对象、单文件 `模板.json`、乐观编辑令牌、库锁、事务前后快照、`queryMutation` 和不可变版本包。`cover-jobs.mjs` 已采用“不可变请求/收件先落盘，最后用元信息事务登记引用”的方式。`model-v5.mjs` 的业务模型并不负责模板元信息；无需往工作空间或内容对象中加模板任务。

采用 **库描述符仍为 v5，模板元信息增加 schemaVersion 2**：

- v1 模板按原样读取；投影视图将缺少的 `templateJobs` 解释为空，不因读操作写文件。
- 首次创建学习请求时，在同一模板事务内将该模板升级为 v2，初始化 `templateJobs`。普通导入和未参与学习的模板继续保持原版本。
- v2 只增加 `templateJobs`；验收记录放在相应 job 内，不能只存一个会覆盖历史的全局 `acceptedStudy`。原有 `versions/currentVersion/derivedFrom` 结构不变。
- `metadata()` 明确认可模板 v2；v1 必须拒绝携带 `templateJobs`，v2 必须完整校验它。事务禁止模板元信息版本回退。
- 旧 v5 读器的 `metadata()` 只认可模板 v1，因而对新模板元信息或其事务返回 `FORMAT_UNSUPPORTED`，不会静默忽略新状态后覆盖。界面说明“此模板由新版插件创建，请更新配套工作台和插件”。这不是整个库已升级到 v6，也不声称旧版还能完整使用此库。
- 本方案不需要新的对象种类、事务版本、库级迁移屏障。若实施改变以上旧读器拒绝前提，必须改用库级版本升级，不能用 v1 扩展字段维持表面兼容。

目录位于 `模板/<templateId>/学习任务/<requestId>/`，包括不可变 `请求.json`、`输入/<assetHash>`、`尝试/<attemptId>/交接.json`、受限 `inbox/`、`收件/<receiptHash>/回执.json`、`规则证据.json`、`校验报告.json` 与还原图。这里只存被模板元信息引用的不可变证据；目录存在不意味着任务已登记或成功。不得另写独立可变 `状态.json` 作为第二真源。库外 native handoff 仍仅作机器定位信封。

## 固定数据与状态

请求 `nova-template-request@1` 固定以下字段，精确字段校验并计算规范 JSON 的 `inputHash`、实际请求字节的 `requestHash`：

- `libraryId, templateId, requestId, createdAt`。
- `template:{id,version,packageHash}`；复制该版本 definition 与 resource 清单，不读取后续 currentVersion 替代原始版本。
- `styleAssetHashes`：按原组顺序固定，去重且非空，全部属于该版本的 style 资源；一期学习整组样张，最多 50 张，与现导入上限一致。
- `inputs`：各图片摘要、类型、字节数、像素；输入副本校验摘要，保留稳定输入。
- `restore:{sourceAssetHash,width,height,outputFormat:'png'}`：一期固定还原首张参考图，尺寸取经过完整解码的该图显示尺寸；明确展示“学习整组，先还原第 1 张验收”，不要暗示已逐张还原。首张超出生成尺寸上限时在开始前明确阻止，不能无声裁切或换图。
- 固定协议 `nova-template-execution@1` 与 scope `template-study-restore`，可选用户补充说明必须有长度上限并进入 hash。

每个 job 存 `id,inputHash,requestHash,createdAt,activeAttemptId,attempts,acceptance`。每个 attempt 存 `attemptId,host,sourceAttemptId,reason,status,createdAt,updatedAt,handoffHash,receiptHash,reportHash,resultHash,failure`。状态沿用 `created/claimed/committed/failed/cancelled/superseded`；`committed` 仅表示证据已提交，展示为“待人工验收”，不能显示“已学会”。未提交时三个结果摘要为 null，提交后均必须存在且互相可核验。

同一个模板最多一个活跃尝试，包括不同请求之间；新建尝试时在模板的同一事务中将旧活跃尝试标为 superseded，再登记新的 host。不同助手继续必须生成新 attempt 和交接，保留前次 host、原因、失败及已提交结果，不原地改旧 host。已验收 job 不再开新尝试；重新学习创建新请求。重复打开助手沿用已有活跃 attempt。

`acceptance` 为 null 或 `{requestId,attemptId,requestHash,resultHash,sourceTemplate:{id,version,packageHash},acceptedTemplate:{id,version,packageHash},acceptedAt}`。这些字段均必须回指本 job 的 committed attempt 和真实版本包；不能只保存 `accepted:true`。

## 有限核心 API 与执行命令

新增 `file-library/template-jobs.mjs`，用 index 注入已有锁、事务和路径/资产/版本包工具，结构参照 `coverJobMethods`。不抽取通用任务框架。返回值中的 `template` 为模板读结果，包含 `id/revision/editToken`；对外 CLI 可裁剪正文。

| API | 输入 | 输出与约束 |
| --- | --- | --- |
| `createTemplateRequest(templateId,input,editToken,{mutationId})` | `{version,notes?}`，其余输入由库解析 | `{template,request}`；mutationId 重放先于新状态检查；固定整组资源、首张还原目标 |
| `createTemplateAttempt(templateId,requestId,{host,reason?},{mutationId})` | host 仅 codex/workbuddy | `{template,request,attempt,handoff,inbox}`；新 attempt 同事务替代旧活跃尝试 |
| `readTemplateContext(templateId,requestId,attemptId)` | 固定三个 ID | 请求、版本定义、全部输入本地路径、attempt/handoff/inbox、历史结果摘要；不执行助手 |
| `claimTemplateAttempt(templateId,requestId,attemptId,input,{mutationId})` | `{host,requestHash,readAssetHashes}` | 校验 host 和全部输入摘要，created→claimed；这些是助手声明，不能声称服务器证明了图片已理解 |
| `commitTemplateAttempt(templateId,requestId,attemptId,receiptBytes,{mutationId})` | 下述受限回执 | 完整验证并整批登记，返回 `{template,requestId,attemptId,result,report}`；没有自动验收 |
| `failTemplateAttempt(...,{code,message},{mutationId})` | 有界错误码与文本 | 活跃尝试终止，保留历史；失败不能携带可用结果引用 |
| `cancelTemplateAttempt(...,{mutationId})` | 固定尝试 | 活跃尝试取消 |
| `acceptTemplateResult(templateId,input,editToken,{mutationId})` | `{requestId,attemptId,requestHash,resultHash,sourceVersion,sourcePackageHash}` | 单次人工业务写入，返回新版本与完整 acceptance |

`queryMutation` 复用既有实现；恢复返回的 `objectKind` 必须是 template。所有写 API 都接受稳定 mutationId，不能因 CLI 未传递 options 破坏恢复能力。

新增 `run-node template` 命令，仅有 `help/doctor/create/attempt/context/claim/submit/fail/cancel/status`。`create/attempt` 可供明确绝对库绑定调用；助手通常仅用 `context/claim/submit/fail --handoff UUID`。路径模式只接受 `--library ABS --template ID --request UUID --attempt UUID` 与必要的 `--file/--stdin`。写输入一律携带 mutationId。提交回执也固定 mutationId，重发使用完全相同字节。

**不提供助手可调用的 accept 命令**。人工验收通过桌面受限 IPC 调 core API，防止执行 Skill 自己验收自己。桌面直接完成 request/attempt 创建，因此常见用户流程不要求手写 JSON 或命令。

## 规则、图片与人工验收

回执精确字段：`format,schemaVersion,libraryId,templateId,requestId,attemptId,requestHash,host,mutationId,rulesFile,restoreFile`。两个文件只能是当前 inbox 中的单层安全文件名，不接受绝对路径、路径穿越、链接或任意库路径。回执至多 64 KiB；规则 JSON 至多 256 KiB；还原图不超过现封面单图限制。

规则证据 JSON 使用受限形状：`fixed:string[], variable:string[], evidence:{sourceAssetHash,ruleType:'fixed'|'variable',ruleIndex,observation}[]`。数组、文本长度和索引均有上限；fixed 非空，每一条规则至少有一个来自固定参考组的 evidence，sourceAssetHash 必须在请求内。AI 不得自行修改 `accepted/aiTested`、版本号、来源说明或传任意 definition 补丁。结构校验不能替代人工判断规则是否正确。

提交先验证 claimed 且活跃、host/request 绑定；稳定读取规则和图片，完整解码 PNG，核验显示像素与请求一致。禁止将任意原参考图片相同字节直接当还原图。异步解码后回到锁内重新核对库身份、活跃尝试、固定模板包/输入摘要、相同请求和回执；然后写不可变证据、内容寻址图片资产及单个元信息事务。只更新摘要引用后才算 committed。规则错误或图片失败不得留下半个成功结果。

人工验收页并排展示固定参考图、还原图、固定/可变规则及证据；标明模板名、源版本和助手。按钮明确“确认规则与还原效果，保存为新版本”。不满意用“重新学习并还原”创建新 attempt，保留旧结果。一期不新增复杂评分表。

accept 在锁内核验 editToken、模板未回收、currentVersion 仍等于用户正在验收的源版本、job/attempt/result 全部绑定、结果文件摘要及源包摘要；用户切走版本或新增版本时返回冲突，保留结果，不把历史结果套到最新版本。

accept 复用 `normalizePackage/installTemplatePackage`，按 `max(versions)+1` 安装新的不可变包：保留原 style 资源和定义中非学习字段；`definition.rules` 写 fixed，明确字段写 variable/evidence，并写入由本次验收派生的 `accepted/aiTested`。同一次 `mutate(...,'template')` 注册新版本、currentVersion 和 acceptance，不能先调用 addTemplateVersion 再单独记验收。新包写入后的未登记残留仍不算成功；同 mutationId 可恢复。内置模板先走现有派生模板路径，不修改内置版本。

封面生成读取已验收新版本时继续固定 packageHash 与规则；模板页的“已记录验收”应优先依据结构化 acceptance 与当前版本匹配。历史导入模板原有布尔标记只能展示为“原模板记录”，不得升级成新执行链已验收。模板新增版本或切回旧版本，不继承其他版本验收。

## 崩溃恢复、备份与兼容

1. 桌面持久化 request/attempt/accept 的固定输入与 mutationId 后再写库；融入既有互斥恢复边界。未得到结果先 `queryMutation`，只允许同输入、同 mutationId 重放；冲突不得偷偷换 ID。
2. 不可变文件写入早于登记；journal 发布前崩溃可能留下未引用文件。它们不进入列表、不当成成功、不自动接管；同操作可以安全重试。journal 发布后的恢复由现有 `recover/applyTransaction/archiveTransaction` 处理。
3. 提交相同 receipt 返回相同结果；同 attempt 不同 receipt 返回冲突。结果校验文件需绑定 requestHash、receiptHash 和 resultHash。已经 committed 的 mutation 重放必须读取历史事务结果，不能选“最后一个 attempt”。
4. `validateRestoredLibrary` 在 template 分支继续校验所有版本包，并验证任务请求、输入、交接、已登记结果和 acceptance 的完整引用图。不能因为当前逻辑在 template 后 continue 而漏检。
5. `prepareRestoredLibrary` 同时处理中断的模板尝试，保留 committed 结果和 acceptance，只将 created/claimed 置 failed，错误码 RESTORED_INTERRUPTED，清除 activeAttemptId。复用 `restore-interrupted` 事务操作并把精确校验扩展到 template；不要直接写模板 JSON。
6. schema4 备份及其事务必须显式拒绝模板 v2。schema5 备份清单仍为原格式，递归收集已有目录即可；备份恢复校验新增模板语义，不能仅凭文件 hash 声称业务证据有效。
7. 恢复继续创建唯一新文件夹，不覆盖或自动切换原库；库外机器 handoff 不随备份成为有效权限。旧信封的 rootIdentity 对恢复目录不匹配，新位置只能由桌面重新建 attempt/交接。
8. 旧 v1 模板无任务，不伪造已学习事实；未知 template 元信息版本返回 FORMAT_UNSUPPORTED。required 包继续拒绝真实业务读写，不能借学习流程绕过授权门禁。

## 留给统一验证的验收条件

后续验证应覆盖：v1→v2 惰性升级与旧读器拒绝；同 mutationId 同输入返回原事务、不同行为拒绝；跨 request 一活跃 attempt；host 切换保留历史且旧 host 不能迟交；异步解码期间取消/回收/换版本冲突；规则引用越界/未知图片/路径穿越/同参考字节/图像格式与像素不符拒绝；不同 receipt 不能覆盖；人工 accept 的 request/result/源版本绑定与一次性新增版本；安装版本包前后及 journal 前后崩溃；恢复中断模板任务而保留已验收版本；模板任务不增加内容数量、不出现在发布提醒；双宿主各一次真实学习还原和人工验收后用于生成。

本方案只完成源码设计，没有执行上述检查；生成质量、真实宿主能力、备份故障恢复及旧读器行为均待统一验证。
