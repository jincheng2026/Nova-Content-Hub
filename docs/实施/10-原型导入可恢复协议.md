# 浏览器备份首次导入：最小可恢复协议

范围：真正实现 `importBrowserBackup(sourceFile,newDestination)`，仅导入为新的 schema5 文件库；Electron/CLI
共用同一业务接口。本文是只读设计，不是实现或跨平台验收证明。

依据：main ba799b5 的 `browser-import/inspect.mjs` 已实现稳定读取、4 MiB 上限、UTF-8/JSON/Core.validate 和资源引用预检；schema5
工作树 README/实现已提供配置、合集、规格、不可用内容引用、历史批次和历史发布接口。现 `image-validation.validateImage`
明确只接收完整解码的静态 PNG/JPEG/WebP，不能为迁移放宽这一封面收件规则。

## 1. 一个目标、一个持久 importId；查询和恢复不依赖原始文件还在

公开三个有限入口即可，均位于 `browser-import/index.mjs`：

```js
importBrowserBackup(sourceFile, newDestination) // 初次接受，或同一目标/相同 sourceHash 的恢复
getBrowserImport(newDestination, importId?)    // 只读状态；不知道 ID 时由目标预约查找
resumeBrowserImport(newDestination, importId)  // 从已保存原始字节继续，不重新读取 sourceFile
```

返回 `{importId,status,sourceHash,destination,libraryId?,progress,issues}`；状态有限为
prepared/running/blocked/ready/publishing/committed。错误也带可获取的 importId 和现场路径；BUSY 表示同一操作已有执行者，不创建第二份。GUI
在第一次调用前固定用户所选目标，不在每次重试时生成新的目录名；CLI 提供 status/resume。get 不获取会改变现场的业务库读句柄，不触发
pending 恢复。

目标父目录先 canonicalize；目标仅接受一个受限 basename。父目录下用目标名的保守 Unicode NFC + 大小写折叠 hash
建固定预约文件名；原始完整目标名也写入并严格比对。保守折叠可多拒绝两个可能冲突的名字，不能在 Windows/macOS
上放过同一目标的两个别名。预约指向随机 UUID 的同级工作目录，拒绝未知字段/版本与任意路径。两个进程可各自准备原始备份，但只有原子独占发布预约的胜者可以执行业务
CRUD。败者若目标与 sourceHash 相同则返回/接续胜者 importId，否则 IMPORT_CONFLICT。不会按文件路径或 updatedAt 判定相同来源。

准备顺序：稳定读并 validate 原始备份 → 新建唯一工作目录 → 写并 fsync 完整原始字节、sourceHash、版本化操作描述 →
最后原子独占发布目标预约。不要用 O_EXCL 直接写最终预约正文然后暴露半截 JSON；采用同目录临时文件写全后 hard-link
独占发布，或现有已验证的等价私有原子原语，失败时不能退回会覆盖的 rename。预约发布前崩溃留下的孤儿准备目录尚未接受业务导入，也没有任何
CRUD，保留现场即可。预约发布后失去响应，下一次查目标可找到同一 importId。

重复语义只绑定目标与本次操作，不建设全机导入数据库，不禁止用户明确选择另一个目标再导入相同备份。已 committed
的同一预约返回原结果；不会因为重试重新建库。原始 sourceFile 后续变化不改变已接受操作，resume 只使用存档 raw；再调用 start
传入不同 hash 明确报冲突。

## 2. 私有工作目录与锁；原始来源不能成为文件系统指令

建议最小模块：`browser-import/operation.mjs`（预约/锁/状态/安装）、`map.mjs`（固定业务次序和字段映射）、`resources.mjs`（data
URL/内置资源/校验），现有 inspect 保持只读。可以抽取 backup 使用的受限私有发布/路径/流式 hash 辅助函数；不对外暴露 generic
lock、writeFile、任意函数名执行或任意库内路径写入。

工作目录存 operation.json、source.json 原字节、pinned-resources/、stage-binding.json、steps/、ready.json。名称、相对路径、枚举与
JSON 字段全部由本版本生成并校验；未知格式停止，不自动“尽力恢复”。输入中的 script、srcPath、file URL、http (s)
URL、模板下载地址均只作来源文字，不 eval、import、fetch、shell 或按路径读取。只执行随应用发行的 Core.validate 和明确内置业务代码。

操作锁覆盖整个 async 导入执行期；复用现有带进程身份/存活判据的锁算法，不以经过几分钟作为可强抢证明。锁顺序固定为
operation → 短时 library；完整图片解码、等待和大文件复制不包在库锁里。现核心同步 locked 回调不可传 async（否则 Promise
返回即释放锁）；若复用必须有明确 await/finally 的外层所有权。锁状态本身不进入最终库快照；锁陈旧恢复失败需呈现原因，不能创建新
importId 绕过。

所有受控路径拒绝 symlink、特殊文件、parent escape、Windows 保留名、尾空格/尾点、`<>:"|?*`、大小写/NFC 冲突与超界路径。父目录可从用户选择的
alias 解析到真实目录，但随后绑定真实父 dev/ino；工作目录/已绑定 stage/目标 dev+ino
一旦改变即停止。输入源文件不能位于目标内；目标不能与现有操作/stage/已存在库重叠。拒绝非空目标，不能仅检查有无 descriptor。

## 3. CRUD 的可恢复点是业务 mutationId，不是“已处理到第几项”

先在工作目录内建立一个新 schema5 stage。createLibrary 若在 descriptor 前失败会留下非空半库：不删除它、不对它重跑
createLibrary；重新建立另一个 stage candidate，只有 createLibrary 完成后才能独占发布 stage-binding，随后才允许任何业务对象创建。绑定前的
candidate 是保留的初始化孤儿；绑定后 stage 丢失或被替换必须停止，不能换一个新库继续旧 IDmap。新 libraryId 生成一次并由绑定固定，浏览器
libraryId 只是 source。

每个有限业务步骤在调用前持久保存 intent：稳定 stepKey、随机 mutationId、固定方法枚举、规范化输入、目标 ID、准确的 expected
editToken 和依赖步骤结果。先 fsync intent，再调用 CRUD，再保存结果。恢复先 queryMutation (mutationId)：已提交则从其历史结果重建
IDmap/结果；未提交才用原封不动的输入和 token 重试。不能拿最新 token 改写已持久步骤，也不能看到一个近似名称便猜测上次已成功。输入/mutationId
摘要不一致、并发编辑或未知事务格式都停止。

返回整个 owner 的追加方法（渠道/候选/规格等）须从该 mutation 的历史返回值与持久的 before 证据求出新增
ID，不能从最新对象最后一个元素猜测。asset import 可按实际内容 hash 复用；唯一已注册对象仍通过 CRUD 接续，未登记的同 hash
孤儿文件不是新业务对象。mutationId 与 IDmap 不能源自旧 ID 冒充 UUID。

IDmap 用有作用域的 source key，例如 project/<pid>/material/<mid>/candidate/<cid>、project/<pid>/post/<postid>
/published-cover、trash/<trashid>/...；目标 IDmap 是已提交 steps 的投影。mappingVersion 固定在 operation
中；不同版本程序必须明示不兼容，不能偷偷用新映射逻辑接续一半旧计划。只允许固定 mapper 方法，不能把 steps JSON 当任意 RPC
队列执行。

迁移次序固定：资源分类/解码和可恢复报告 → 模板/照片/提示词 → 配置与渠道 → 内容及基础正文/附件/规格/候选/历史批次 →
合集及成员 → 每渠道计划 → 历史发布 → 默认项 → 软删和历史任务记录 → 全量对照。配置默认关系最后设置。软删对象先构建真实业务数据与关联，再走相应
trash API；不能因为最后在回收站就仅归档其 JSON。集合成员删除约束须按依赖次序处理，不能通过内部写文件绕开。

TASKS 只形成明确的“导入历史任务/旧状态”记录，旧 running/active/attempt 不恢复为当前运行，也不生成可信 provider receipt。旧
pending 与新 stage CRUD 的事务 pending 是两回事：新 stage 的 pending 必须由核心恢复并清空，不能把它们作为可忽略的旧任务。

## 4. 资源：原字节保真与完整解码分开，但缺文件不能被伪造成可用

对嵌入 data URL 严格限定媒体类型/编码并验证解码完整性、大小上限；实际 magic/完整解码决定类型，不能信任扩展名、data MIME 或旧
px/hash。保留解码后的原始压缩文件字节和 SHA256，不缩放、不转码、不移除 EXIF；预览衍生物以后再做，不能替换源资产。每个资源的解析结果及实际
hash 持久化，重复引用可按 hash 共享文件。Core.MAX_BYTES 是本轮接受备份上限，不为兼容 silently 提高；体积拒绝应报限制而非损坏。

内置路径只能查应用随包的精确 catalog：允许的旧 source 标识 → 固定可信包资源 + 预期 hash/角色；不得用来源字符串 join
文件系统。将用到的可信资源复制并固定在工作目录，再以实际 hash 供迁移使用。恢复不依赖应用后来恰好仍有同一个目录；catalog
版本/hash 不同不能无声换图。任意外部 URL/本机路径均 unavailable，用户补文件是后续明确操作。内置 SVG
结构示例不能当真人照片或解码后的生成封面；SVG 仅按既有结构资产规则保留。

新增内部 `validateImportedRaster`，不要改现 `validateImage` receipt 合约：

- 静态 PNG/JPEG/WebP 复用现有严格完整解码校验，保留原始 bytes；显示宽高按 EXIF 朝向计算，像素结果不回写源文件。
- GIF、animated WebP 使用已存在 sharp 解码器显式 all pages/animated，failOn warning；读取全部帧的像素输出直至正常结束，不能只
  metadata 或第一帧。用 sequential 流式 drain/计数避免将所有帧 raw Buffer
  留在内存；验证帧数、每帧尺寸和实际输出总量，声明并测试编码体积/像素总量/帧数限额。stream 本身不保证 libvips
  无内部缓冲，因此限额与逐图处理不可省略。
- PNG 的 acTL/APNG 不得交给只能证明静态首帧的路径后声称完整验证。当前最小实现明确 unavailable/unverified+原因，原字节保留；若首发要求
  APNG 全帧可用，这是必须增加经验证解码能力的具体缺口，不能临时自造解码器或放宽 receipt。新依赖只有能力核验确实证明现 sharp
  不能满足必需格式时另作选择。
- 完整解码失败的真实上传保留原字节与原因，活动模型明确
  unavailable；不能拿缩略图或首帧替换后宣称导入成功。缺解码器是执行能力阻断，不把所有资源降级后返回普通成功。限额超过与损坏分别报告。报告统计
  available/unavailable/unsupported，不以一个“完成”掩盖差异。

Sharp 官方说明 all-page 图像以纵向多页像素表示，`pages:-1`/`animated:true` 支持全部 GIF/WebP 帧；其 metadata
与输入像素限额不能替代实际像素读完：[constructor](https://sharp.pixelplumbing.com/api-constructor/)、[output](https://sharp.pixelplumbing.com/api-output/)
。实际安装版本/编译能力仍需用真实多帧 fixtures 验证。

下一执行单元在真正导入前闭合两个有限接缝，不插入本轮已冻结 schema5 回归：

- 照片仍以照片目录为唯一真源。补 photo schema2 和
  `createUnavailablePhoto({title,isOwnPhoto,originalName?,source,reason},{mutationId})`、
  `resolvePhoto(photoId,{assetHash},token,{mutationId})`。schema2 明确 available + 真实 hash，或 unavailable + assetHash:
  null；旧 schema1 读取投影为 available，不重写历史。resolve 完整核验真实资产后沿用原照片
  ID、声明、来源和软删状态，不自动设为本人、不自动恢复或默认选择。读/列表/软删/恢复都能处理 unavailable；setGenerationDefaults
  拒绝不可用照片，defaultIssues 增加 unavailable，cover request 明确拒绝它，不能依赖 null hash 在更深处偶然报错。缺文件的旧默认选择愿望保存在
  IDmap/report，不绕过默认 API；补文件后用户明确设默认。profile.avatar 无字节时保持 null，原值进 profile 来源报告，不在
  workspace 再复制一套照片对象。
- 缺图模板使用现 `createTemplate({resources:{},definition:{...原结构,importMissingReferences:[...]}})`
  ，或仅包含已获得的真实资源；missing 描述是不可用证据，不是假资源 entry/hash。空资源包仍有正常的新包
  hash/版本，二者只是本次创建事实，不能当作旧模板历史版本。现 request 要求非空、属于固定包版本的
  styleAssetHashes，因此空包无法生成；无需往某个无关内容的 unavailableReferences 挂模板引用。若包有部分有效样张，应由具体缺失角色决定是否可用，不能仅凭
  importMissingReferences 存在就笼统断言所有用途可生成或都不可生成。

这两个接缝与当前有限 CRUD 无必然冲突；照片状态需同步核心 schema/资产遍历/备份验证等读取路径。旧失效照片不能只归档 raw
后计为已迁移照片。无需为这几类设计通用迁移实体框架。

## 5. 历史证据与当前选择分别迁移

当前 post.text 进当前计划，date-only 保持 date，缺时区 local-minute 保持 timezone:null；不补当前机器时区或午夜。recordedDate
保留旧录制日期；新文件 createdAt 是本次建对象时间，不能冒充原记录时间。host/showSample 仅为可选机器偏好建议，motion 不在备份
SETTINGS；installation/trust/auth/client/session 永远不变成正式安装/授权事实。

`recordHistoricalPublication(subject,{planId,schedule,publicationText:null,cover,source,url?,channelName?},token,{mutationId})`
与合集对应入口记录历史。旧 pub 未冻结文案，所以 null；不能取当前 post.text。pub.snapshot.img 是独立冻结资源，必须独立解析并比较实际
SHA：仅在 bytes/hash 相等且语义不矛盾时复用已注册具体候选；旧 candidateId 相同而图不同则登记单独的历史候选，用它记录历史，绝不更改当前规格/主选图。无字节/坏字节则
cover:null 并记录 unknown/unavailable 证据，不能补当前候选或只有同名的 builtin 图。模板历史版本没有证据就保持未知。

库内最终保存 `系统（别动）/导入/<importId>/` 的原始备份 bytes、带作用域 IDmap、资源结果和迁移报告及其 SHA256。这是固定业务
provenance 写入步骤，不是公开任意文件写入接口；不复制 operation 活锁与工作目录绝对路径作为可执行配置。schema5
文件库的正常列表、读取、编辑、发布/恢复 API 必须真实看到对应活动与回收站对象。

## 6. READY 冻结后安装到目标，descriptor 是唯一提交点

所有对象步骤完成后：恢复 stage pending、验证业务引用/计数/来源到目标逐项对照；在操作锁下确保没有工作者继续写 stage；生成
ready.json：importId/sourceHash/mappingVersion/libraryId、完整相对路径+文件 bytes/SHA256 清单、descriptor 原 bytes
hash、IDmap/report hash。目录和每个文件均做受限 inventory，排除且仅排除已知活锁。校验流式进行，不一次读全部资产/历史正文。

目标可为不存在，或用户指定的真正空目录（均视为“新库”）。mkdir 后、写任何目标字节前，持久记录目标 parent/root dev+ino 绑定；崩溃在
mkdir 与绑定之间时，只能重新将该目录验证为空再进行首次绑定，不声称它已属于本操作。绑定一旦存在，目标消失或替换必须报
TARGET_CHANGED，不能以仍为空重新认领。此规则避免 mkdir 后空目录无法恢复，也没有覆盖已有数据的权限。

按 READY 清单复制到绑定目标，descriptor 暂不发布。每文件临时写入、fsync、hash 核对、独占发布；已有文件仅在属于这个绑定安装且与
READY hash/长度严格相同才可继续，不覆盖任何异值文件。临时文件名/所有者也有固定协议；未知新增文件使安装停止。跨卷使用复制，不依赖跨卷
rename；原始源文件所在卷无关。

最后在同一操作锁下重查目标身份、全量 inventory/hash、stage/READY 证据和导入 receipt，然后独占发布 descriptor（复用私有
descriptor-last 原语，禁止可覆盖 rename）。descriptor 之前即使大半文件已到目标，openLibrary 也不得承认它是完整库。descriptor
发布之前出现权限/盘满/中断都是未提交，保留可查现场。descriptor 已发布但结果日志/cleanup/fsync
后续报错时必须先核对提交事实，不把结果降成“失败可重新导入”。

恢复见到 descriptor 原 bytes/hash 与 READY 一致 + 已绑定目标身份 + 固定 import receipt/libraryId/sourceHash 相符即判
committed，补写操作完成记录，不再执行 CRUD。这是 descriptor-last 的提交证据：即使操作完成日志还没写，也不能再要求当前全库等于
READY（另一进程可能已经打开并正常编辑了已提交库）。当前文件完整性可另行核验并报告变化，但不撤销已发生的导入提交、不重新覆盖。root/descriptor/import
receipt 不匹配要报告结果被替换或证据不足，绝不自动重建；已有 durable committed 记录时，即使库此后正常升级
descriptor，也仍返回原完成事实并单列当前目标变化，不把升级当成可重新导入的失败。UI 在自动打开库前查询提交状态，仍必须支持“descriptor
已成功而调用方没收到响应”的恢复。

不能承诺阻止恶意进程在最后检查与 descriptor link 之间任意替换文件；普通外部编辑通过反复身份/清单校验识别，导入目标在
commit 前不提供编辑入口。若要求对恶意同用户进程也有强快照保证，需额外 OS 原语，不应在本单元虚构实现。Windows 不支持目录
fsync 时如实限为已验证的进程崩溃恢复，不把 macOS 结果称作 Windows 掉电安全。

失败不自动 rm -rf stage、半成品目标或源存档。最小首版连成功现场也可保留；清理是另一个明确受限操作，不把清理成功当提交条件。用户只需要
status/resume/选择另一个新目标，无需手改 JSON。已绑定目标发生异值变更时停止并提示现场，不能以“修复”之名覆盖用户数据。

## 7. 必须覆盖的有界验收与实现顺序

1. 先 operation/预约/status/resume：同目标同 raw 双进程只接受一个 importId；不同 raw 冲突；进程死于 raw/stage
   绑定前后仍能明确查询。源文件移走、内容变化后 resume 使用存档原字节；未知操作版本/任意路径/符号链接/大小写与 Windows
   名字拒绝。
2. 再资源入口与纯字段 mapper：真实 JPEG EXIF、PNG、静态/动画 WebP、多帧 GIF；截断最后一帧、metadata 正常但像素坏、解码限额、缺
   sharp；data MIME 伪装；builtin 改包；URL/srcPath/scripts 全无执行/访问。验证导入后源资产 SHA 与上传 bytes 完全相同。
