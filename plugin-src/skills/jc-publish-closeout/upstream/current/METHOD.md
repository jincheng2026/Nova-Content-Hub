# JC Publish Closeout

## 边界

这是发布后收口 Skill，不是内容生产总管。

只做：

```text
确定刚发布的视频
→ 冻结真实发布资产
→ 自动发现三平台作品
→ 建立唯一档案
→ 创建 12h / 7d 监控任务
→ 沉淀入库（复制文本资产到知识库）
```

禁止：

- 不介入写稿、拍摄、剪映、AI 剪辑或 Remotion 剪辑；
- 不修改、移动两个剪辑项目；
- 不在发布后生成或改写标题、简介、封面文字；
- 不要求用户填写作品 ID、链接和发布时间；
- 不把「预期全平台发布」写成「已经全平台发布」；
- 不自动触发，只有用户显式调用才运行；
- 不修改 `.bets/` 押注内容，归档押注前后必须校验 SHA-256 一致。

核心脚本位于本 Skill 上两级的 `content_feedback.py`。每次先解析本
`SKILL.md` 的真实路径，再定位脚本，不依赖当前工作目录。

## 2026-09-27 起：抖音发布后自动建档（先读这一节）

9 月 6 日起发布的视频一条都没建档（原来的两条建档路都断了，查新还每轮报「没有未建档新作品」），
所以抖音这一路改成了自动收齐，本 Skill 的手动流程主要用来补资料和处理歧义。

- **自动建档**：定时任务每 4 小时查一次抖音作品列表（1.0 的 `scripts/wechat_publish_signal.py` 调
  `scripts/douyin_auto_register.py`）。列表里有、但没有档案的作品：开关打开时直接建档（目录「发布日期-短标题」，
  发现起点是真实发布时间，标题和简介取平台原文），关着时只如实报数。开关文件：
  `个人IP与内容/内容数据统计/.runtime/publish-automation.json` 的 `douyin_auto_register.enabled`。
  疑似和已有档案重复、作者不是本账号、不是视频、早于起点（`since`）的一律不建，报出来。
- **自动认回资产**：建档后同一轮里，`recover_local_covers.py` 拿平台封面逐像素比对，从「下载」、桌面、文稿、
  第二大脑和 Codex 出图目录（`~/.codex/generated_images`）认回封面原图。原件只做 APFS 克隆。
- **成片不进档案**（2026-09-27 锦成拍板）：成片随时能用 TikHub 从平台下载，档案不再存成片、源片，也不算缺项；
  `recover_local_videos.py` 的开关 `video_recovery.enabled` 已关。旧档案里已有的成片不动。
- **已有封面也和线上比**：`check_existing_covers`（开关 `cover_check.mode`：off / report / apply）。平台后来换了封面时，
  新封面存成 `cover_douyin`，`cover_vertical` 保持发布当天那张。
- **作品编号**：登记单顶层 `work_id` 记第二大脑选题编号（T011 这种）。自动建档时为空（待认领），用
  `content_feedback.py set-work-id --project-dir <档案> --work-id T0xx` 写，不要直接改登记单。
  注意 `content_id` 是待发布包编号，不是 T 编号。
- **12 小时、7 天数据**：到期时先取本机抖音创作者中心采集库（`~/.hermes/douyin_stats.db`）观察点之后的第一条
  （晚得不多才算），其次调 TikHub，都不行就在观察点写 `missed_reason`，以后不再生成任务。
- **补档**：已发布却没建档的，按核对过的清单用 `scripts/backfill_published.py --plan <清单> [--dry-run] [--only T0xx]`，
  整段拿 `run-cycle.lock`，可重跑。2026-09-27 用它补了 9 月 9 条，清单和回执在
  `内容数据统计/.runtime/closeout-20260927-backfill/`。
- **改已有档案**：换封面用 `adopt_verified_legacy_assets.py --replace-cover`（旧文件挪进档案的
  `.system/evidence/cover-history/`，不删），改登记角色用 `--relabel FROM=TO`。`--final-only`（只收成片）是旧功能，
  成片不进档案后不再用。
- **沉淀入库**：第 6 步用 `scripts/sink_knowledge_base.py`（只新增条目、台账一条视频一行，没校正版逐字稿的跳过）。

## 一次调用流程

### 1. 汇合本条视频候选

读取：

- `个人IP与内容/内容创作/` 中最近的成稿、封面和发布素材；
- `Documents/AI剪辑/analysis/` 的 case manifest 与最终成片；
- `Documents/remotion剪辑/` 的工程、成片与状态；
- Downloads 中最近的 MP4、SRT、封面。

不能只按修改时间或 `0721-03` 识别。综合选题、发布时间、时长、文件哈希、封面和上游
case 证据。只有多个候选或证据冲突时，把全部歧义合并成一次确认。

### 2. 建立归档

标准目录：

```text
YYYY-MM-DD-选题/
├── 内容.md
├── 字幕.srt
├── 封面-竖屏.png
├── 封面-横屏.png
└── .system/
    ├── manifest.json
    ├── snapshots.jsonl
    └── evidence/
```

特殊情况真实存在时才增加 `候选/` 或平台专用封面。成片、源片不进档案（2026-09-27 起，需要时用 TikHub 从平台下载）；
2026-09-27 以前的档案里已有的 `成片.mp4`、`源片.mp4` 保持原样。

真正合并不由 Skill 文字手工拼文件，统一运行事务脚本：

```bash
python3 <content-feedback-loop>/scripts/finalize_published_content.py \
  --project-dir <已发布单视频档案> \
  --pending-dir <jc-chendian 待发布包> \
  --db <content-feedback.sqlite>
```

脚本合并 `content_id` 和 `video_id`，通过平台时长、发布日期、同目录封面和
`archive_key` 找回乱名资产。成片只用来定位同一文件夹里的字幕和封面，本身不复制进档案；
多个成片同等匹配时只返回一次合并候选，不擅自选择。
资产使用 APFS 克隆，复制后校验 SHA-256、媒体规格和可解析性。成功后只把
待发布包移入可恢复的 `.trash`；剪辑工程、Downloads 和其他原始资产不移动、不删除。
任何失败都恢复 manifest、`内容.md` 和本次新建的资产。

### 3. 冻结发布事实

`内容.md` 是人看的唯一 Markdown。完整逐字稿、真实标题、简介、封面文字、平台实际版本、
原工程位置都写在其中。

正式档案中的逐字稿只允许保留校正版，统一写入 `内容.md` 的「完整逐字稿」。
转写统一用 `jc-zhuanxie`（火山引擎，失败自动改用本机 Qwen3-ASR），对成片转写后校正，不拿录制前的稿子代替。
成片用本机找到的那份，找不到就用 TikHub 从平台下载一份放 `.runtime` 转写，转完不进档案。
拿不准的字先看成片画面上的烧录字幕（按时间点抽帧），字幕是锦成剪辑时定的文字，比两遍识别都准；
字幕因消音改写的（例如把「小红书」写成「小某书」），逐字稿跟字幕走。
原始识别、分段转写、模型 JSON 和校对中间稿只能放在 `.runtime`
或系统临时目录；校正完成后不得复制进 `视频项目/`。正式目录发现这些文件时，
本次归档视为未完成，必须先移入可恢复的 `.trash` 再验收。

`.system/manifest.json` 只保存结构化事实。发布后只读取和归档，不补写历史。

`内容.md` 的程序区由稳定标记包围。每次更新前校验上次程序区哈希：

- 哈希一致：只替换程序区；
- 哈希不一致：立即停止并报告冲突；
- 程序区以外的人工文字必须逐字节保持不变。

成功写入正式档案后，把对应待发布内容包的全部 `event_id` 标记为 `consumed`，在正式
项目 `.system/evidence/chendian/` 保存回执证据，再把待发布内容包移入可恢复的 `.trash`。
正式档案校验未通过时不得提前关闭或移走内容包。

### 3.5 归档发布前押注（如有）

检查 `视频项目/.bets/` 是否有与本条视频匹配的押注文件（按选题与日期判断）。
有则移入本视频档案 `.system/押注.md`：移动前后 SHA-256 必须一致，并在
`.bets/index.jsonl` 追加一行标记 `archived_to`。押注内容一个字不改。
没有押注不是错误，不要求补写。

### 4. 自动发现三平台作品

默认 `expected=true`：

- 抖音；
- 小红书；
- 视频号。

只有创作者中心真实找到作品后才写 `discovery_status=found`。作品事实与采集故障分开：

```text
publication_status: unknown / pending / published / rejected
discovery_status: searching / found / not_found / ambiguous / auth_error
```

匹配至少综合标题、发布时间、视频时长、封面和平台作品 ID。高置信度且第一、第二候选
分差足够才自动绑定；低置信度宁可 `not_found`，不得误认。三个平台的歧义只问一次。

把每个平台的只读候选保存为 JSON：

```json
{
  "candidates": [
    {
      "post_id": "真实 ID",
      "title": "真实标题",
      "published_at": "ISO 时间",
      "url": "真实链接",
      "publication_status": "published",
      "duration_seconds": 45
    }
  ]
}
```

再运行：

```bash
python3 <content_feedback.py> ingest-discovery \
  --project-dir <单视频目录> \
  --platform douyin|xiaohongshu|wechat_channels \
  --evidence <候选 JSON>
```

当前正式验收通道：

- 抖音：登录态下的抖音创作者中心作品管理；
- 小红书：2026-09-27 起走 TikHub 本账号笔记列表（`scripts/tikhub_xiaohongshu_adapter.py`，账号「何锦成本人」），
  每 4 小时查新时按时长为主、标题为辅自动认领，12 小时 / 7 天点自动采；认领不上的（档案没记时长、标题改写大）
  核对后用 `ingest_confirmed_discovery` 写明依据；登录态创作服务平台看板仍可人工补充；
- 视频号：TikHub 窄通道或经过真实账号验收的只读通道。

不得把公开搜索、分享页抓取或模拟数据称为自动发现。

### 5. 启动监控

作品发现期从调用开始，默认 72 小时。截止时冻结第一次总复盘的平台集合：

- `final_review_at = 集合中最晚 published_at + 7d`；
- 截止后才发布的平台只生成补充复盘；
- 不改写第一次总复盘。

后台每 4 小时醒一次，但只在以下任务到期时访问平台：

- 待发现作品；
- 各平台真实发布时间后的 12 小时观察点；
- 各平台真实发布时间后的 7 天观察点。

每条快照同时保存 `target_at`、`collected_at`、`age_hours`、`delay_reason`，不得把延迟采集
伪装成精确的 12 小时数据。

**口令留资判决（7 天观察点附带动作）**：若逐字稿结尾带口令（「评论区回复『XX』」句式），
7 天点采集时数抖音评论区刷该口令的条数记入档案；本条视频若源自某张评论区洞察卡
（jc-comment-visualize 快版），把「本次是否有效＋留资数」回写到那张卡。执行会话再按
`锦成知识库/00-锦成IP库/05-判断逻辑库/创作协作与复盘要求.md` 的 E08—E09 处理：单条数据只补案例，不直接宣布某个写法永久有效或永久失效。
同时回看 `教程视频迭代/feedback.md` 中本条视频（按关联内容匹配）标「待观察」的条目，
按 7 天真实数据在该条目追加一行判决「验证有效／没效果＋依据数字」，不改写原记录。

### 6. 沉淀入库

归档冻结成功后，同一次调用内把本条视频的文本资产复制进知识库（只复制，不移动、不改写
原档案；成片、源片、封面图、字幕等媒体文件一律不复制）：

- 生成 `锦成知识库/LLM-Wiki/原始资料/锦成口播视频/YYYY-MM-DD-选题.md`：完整逐字稿、真实标题、
  简介、封面文字、已发现平台链接，末尾带 📌来源（指向本视频档案路径）与 🎯应用 双标签，
  条目格式对齐该目录已有条目与其 `README.md`；
- 在 `锦成知识库/01-业务库/锦成IP内容/08-数据复盘.md` 的「已发布视频台账」追加本条一行
  （发布日期、标题、封面文字、`[[逐字稿条目]]` 指针），抖音、视频号、小红书三格数据列已采到数就先填上，没有就留「—」；
- 7 天数据由数据采集后台每轮自动回填台账同一行，本 Skill 不再手动回填，也不新增第二行。

真源仍是视频项目档案；知识库条目是写稿会话的供血副本，两处不一致以档案为准。沉淀失败
不阻塞收口主流程，但必须在完成报告里写明「沉淀未完成」，禁止静默跳过。

### 6.5 同步到第二大脑

正式档案冻结后，同一次调用内运行：

```bash
python3 <content-feedback-loop>/scripts/sync_second_brain_archive.py \
  --projects-root "/Users/hejincheng/AIJinCheng/个人IP与内容/内容数据统计/视频项目" \
  --output-dir "/Users/hejincheng/AIJinCheng/个人IP与内容/第二大脑/06_发布复盘/已发布视频档案"
```

每条已发布视频生成一份分析 Markdown，并更新 `00_已发布视频总览.md`。
分析副本只保留发布事实、数据、发布素材和校正版逐字稿；不复制成片、封面、
JSON、原始识别、分段转写或校对中间稿。数据冲突时仍以正式档案为准。
同步失败不回滚已完成的发布档案，但必须报告「第二大脑分析副本未更新」。

## 幂等与部分成功

重复调用同一条视频必须：

- 沿用原 `video_id`；
- 不重复建档；
- 不重复创建飞书记录；
- 不重复创建定时任务；
- 不重复写快照；
- 不重复生成知识库沉淀条目，台账同一条视频只占一行。

单平台失败不拖垮整条流程。成功的平台继续监控；登录失效、审核中或未找到的平台保留状态并
重试。

## 停止条件

只在以下情况停止并报告：

- 多个本地视频候选无法安全区分；
- 平台出现登录、验证码、付费密钥或安全策略阻断；
- `内容.md` 程序区哈希冲突；
- 文件校验或迁移回滚失败。

除此之外，不让用户再登记作品，不要求第二次调用。

## 工作台联动

用户在工作台点「我刚发布了」后，视频号发布信号若只找到一个标题精确一致的
`jc-chendian` 内容包，应直接调用上述事务，完成后再显示「已合并」。只有相似匹配或
多个本地候选时才等用户一次确认，不允许继续显示「尚未自动合并」却不执行。
