# 锦成个人业务周报

把分散的聊天、飞书文档、项目资料、截图、后台数据和链接整理成给合伙人及团队成员看的业务周报。固定采用「一次性问卷 → 一次确认 → 自动写入飞书 → 回读验收」，禁止逐题追问。

## 适用边界

- 仅在 `/Users/hejincheng/AIJinCheng/飞书计划` 及其子目录执行。
- 处理个人业务周报、项目周报和内部业务同步，不处理普通公司述职、个人日记或对外营销稿。
- 用户说「更新本周周报」「写周报」「整理个人业务周报」时启动。
- 默认新建飞书文档；用户明确要求修改旧文档时才更新原文档。

## 强制交互合同

1. 先自行搜集证据，再提问。
2. 所有待补问题必须在同一条消息中一次问完，不得一问一答。
3. 收到用户回答后，生成经过合伙人审核的完整初稿，只做一次总确认。
4. 用户回复「确认」「OK」「写入」或给出修订意见，即视为最终确认；吸收修订后直接写入飞书，不再重复确认。
5. 只有新信息产生重大矛盾、会导致错误对外披露时，才允许追加一次合并澄清。

不得出现这类低效流程：

- 每收到一个答案再问下一个问题。
- 已经能从聊天、文档或截图取得的数据，再让用户重复填写。
- 用户已确认后，又把文档标题、图片位置、写入动作拆成多轮确认。

## 工作流

### 1. 建立证据包

按可用性读取：

- 当前对话和用户指定的 Codex 对话。
- 用户给出的飞书文档、项目资料、链接、表格和本地文件。
- 数据截图与视频平台后台截图。
- 必须主动检索并读取上一周已确认的真实周报。它是本周标题、章节顺序、版式、数据呈现颗粒度和表达语气的首要参考；不能只读取抽象模板或 Skill 合同。

格式来源优先级固定为：

1. 用户本周明确提出的新要求。
2. 上一周已确认的真实周报。
3. [references/report-contract.md](references/report-contract.md) 中的兜底格式。

内容取舍、表达和风险处理按 [references/writing-quality.md](references/writing-quality.md) 执行。该文件只提高内容质量，不得改变上一周已确认的标题、章节、表格、标签和整体语气。

不得自动沿用上一周的数据、结论和任务。无法读取上一周真实周报时，把「是否改用兜底格式」并入一次性问卷，不得静默套用新模板。

从上一周真实周报提取并记录一份内部「格式指纹」：

- 标题命名与周期写法。
- 一级、二级章节的顺序和名称。
- 结果总览使用列表、高亮框还是表格。
- 平台数据使用汇总指标还是逐条明细。
- 问题与风险是否独立成章。
- 本周计划表的列数和字段。
- 无协同事项时是保留「暂无」还是隐藏章节。
- 句子长度、判断密度和整体语气。

除非用户明确同意改版，否则以上格式指纹必须延续。不得擅自把简洁周报升级成更正式、更分析化或更复杂的业务报告。

把信息分成：

- `明确事实`：有用户陈述、文档、截图或数据源支持。
- `用户口径`：例如把跨周发布计入上一周、删除视频仍计发布次数。
- `待确认`：缺少且会影响周报正确性的字段。
- `判断候选`：由事实推导，尚未得到用户确认。

同时为每项协作成果标明责任边界：锦成主导、锦成参与、他人负责或团队共同完成。这是内部证据字段；上一周没有对应标签时，不得为此改版。

不要把工程日志、工具操作过程、文件清理和纯努力描述默认写进业务周报。

### 2. 一次性收集全部缺口

完整读取 [references/intake-questionnaire.md](references/intake-questionnaire.md)，根据证据包预填已知项，只问剩余项。

要求：

- 在问题开头说明还需用户回答多少组。
- 给出可直接复制回答的编号模板。
- 允许用户回答「沿用」「无」「没统计」「不计入」「交给某人负责」。
- 项目数量可变；逐项目字段必须在同一张问卷中给完。
- 截图、链接或聊天记录可以代替手填数据。

### 3. 归一化、核算与写作筛选

完整读取 [references/writing-quality.md](references/writing-quality.md)，先保留全量证据，再压缩交付内容：

- 结果总览默认保留 3～5 个最重要结果；业务线较多时不删项目，而是在每个项目内做减法。
- 每项先写结果，后写过程；按对方的决策价值而不是发生时间排序。
- 重要成果至少有一个可验证锚点：数字、日期、产物或链接、截图、相关方反馈。
- 缺少且会影响正确性的锚点进入唯一一次确认；不猜数、不补 0，不得把 `[待填]` 带入最终飞书文档。
- 内部判断每项是仅供知悉、需要决策、需要支援还是已闭环；除非历史格式已有此标签，否则只用于决定内容位置，不显示在正文。

检测延期、未达标、数据下滑、卡住、等待他人、资源缺口等风险。普通风险放入原有「问题与风险」章节；若会影响他人排期、对外承诺、资源安排，或可能被第三方提前告知，同时生成一段建议立即单独沟通的文本，包含事实、影响、可选方案、推荐选择和最晚决策时间。该文本与周报初稿一起进入同一次确认，不增加新一轮问答。

- 区分「独立内容选题数」和「跨平台发布条次」。
- 用户要求全记录时，删除、下架或限流内容仍计入实际发布条次，并说明后续状态。
- 只有明确归因证据时，才把进线、成交归因到单条内容；否则只写全平台合计。
- 平台数据分开统计；缺失指标不补 0，不从模糊截图猜数。
- 计算合计前核对统计周期、重复内容、存量置顶内容和删除内容。
- 计划必须拆成 `任务 / 目标 / 指标`；没有合理量化指标时，用明确交付物作为验收标准。

### 4. 生成完整初稿并做合伙人审核

完整读取：

- [references/writing-quality.md](references/writing-quality.md)
- [references/report-contract.md](references/report-contract.md)
- [references/partner-review.md](references/partner-review.md)

先按上一周真实周报的格式指纹生成完整初稿，再执行合伙人视角审核。不得因 `report-contract.md` 的兜底示例而覆盖已有周报风格。若确需调整格式，必须在唯一一次确认中列出变化并取得用户同意。

审核后的确认稿必须同时提供：

1. 周报标题、周次和周期。
2. 可直接发布的完整正文。
3. 最多一组「请一次确认」清单，只列真正影响正确性的口径、数据或判断。
4. 将 `待确认` 限制在确认消息里；不得把占位词带进确认后的飞书文档。

### 5. 一次确认后写入飞书

用户确认后：

1. 读取 `~/.agents/skills/lark-shared/SKILL.md`。
2. 读取 `~/.agents/skills/lark-doc/SKILL.md` 及其要求的创建、XML、样式和回读参考。
3. 新建飞书文档，按 [references/report-contract.md](references/report-contract.md) 排版。
4. 把截图放到其证明的数据模块下面；同平台同类截图尽量用 grid 并排。
5. 只有用户明确要求时才更新旧文档，且必须局部修改，避免覆盖人工排版。

### 6. 回读验收

创建或更新后必须回读，不得只凭命令成功就交付。

检查：

- 标题、周次和周期正确。
- 标题命名、章节顺序、结果总览、平台数据颗粒度、风险章节、计划表列数、协同事项处理和表达语气与上一周格式指纹一致；用户已明确同意的改版除外。
- 五个固定模块齐全；无真实协同事项时允许隐藏第五部分。
- 开头结果总览覆盖所有核心项目，不只写短视频平台数据。
- 每个平台图片紧跟对应数据，图片数和来源一致。
- 链接可见，数据与确认稿一致。
- 不存在 `待确认`、`待补`、`TODO`、`数据草稿`、`截图未清晰显示`、旧周数据。
- 事实与判断没有混写，判断均有下一步动作。
- 结果总览已做减法，每个核心项目的最重要结果在前。
- 重要成果有可验证锚点，协作成果没有混淆锦成与他人的贡献。
- 不存在形容词代替事实、抽象名词堆叠和无信息量收尾。
- 延期、卡点、未达标和数据下滑已按影响分流，需要立即单独沟通的风险未被埋进普通周报段落。

回读通过后只交付飞书链接、验证结果和仍存在的真实风险。

## 失败处理

- 无法读取某来源：继续使用其余证据，在一次性问卷中集中列出缺口。
- 截图模糊：说明具体看不清哪个字段，不猜数。
- 飞书权限不足：按 `lark-shared` 的最小权限流程处理。
- 飞书写入或回读失败：明确写 `status=qa_failed`、失败阶段、原始错误和下一步；不得包装成完成。
