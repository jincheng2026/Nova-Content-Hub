# 合伙人视角审核

在向用户提交唯一一次确认稿之前逐条审核。

## 0. 历史一致性门禁

- 是否真实检索并读取了上一周已确认的周报，而不是只看 Skill 模板？
- 标题命名、章节顺序、结果总览组件、平台数据颗粒度是否与上一周一致？
- 问题与风险、计划表字段、协同事项的处理是否与上一周一致？
- 句子长度、分析密度和语气是否延续上一周，而不是被改成更正式或更像咨询报告？
- 若存在格式变化，是否来自用户本周明确要求，并已在唯一一次确认中列出？

任一项不满足，先按上一周真实周报修正，再进入后续审核。不得以「新模板更完整」为理由静默改版。

## 1. 覆盖完整

- 结果总览是否覆盖全部核心项目？
- 是否因短视频数据丰富而漏掉直播、课程、产品、商业交付或重大风险？
- 当前推进项目与正文、下周计划是否能一一对应？

## 2. 做减法与结果前置

- 结果总览是否只保留 3～5 个最重要结果？业务线较多时，是否在项目内做减法，而不是直接漏掉整条业务线？
- 每个项目是否先写结果和影响，再补必要过程？
- 重要性排序是否高于发生时间排序？
- 纯工具操作、文件搬运、会议流水和无结果的努力描述是否已删除？

## 3. 事实、锚点与贡献边界

- 数字、时间、发布数量、交付物属于事实。
- 原因解释、趋势、机会和策略属于判断。
- 判断必须能追溯到事实，并注明样本或证据边界。
- 每项重要成果是否至少有一个数字、日期、产物或链接、截图、相关方反馈？
- 协作项目是否区分锦成主导、锦成参与、他人负责和团队共同完成？
- 没有可验证锚点的程度形容词是否已删除，而不是换一个近义词？

## 4. 删除过度包装

| 避免 | 改为 |
| --- | --- |
| 打造成熟体系 | 验证链路，沉淀流程 |
| 完成巨大突破 | 完成 X 项交付，获得 X 数据反馈 |
| 成为核心增长渠道 | 当前数据表现较好，继续验证 |
| 明显碾压其他平台 | 从本周可见数据看，该平台表现相对突出 |
| 这个视频爆了 | 该选题在当前样本中表现更突出 |

额外扫描：

- 删除「赋能、抓手、颗粒度、全链路、方法论」等不承担必要精确含义的抽象词。
- 删除「通过…从而…进而…」式空转和强行对仗。
- 删除「后续将持续跟进」等无信息量收尾；换成具体下一步，或直接删除。
- 问一遍：「这句话换个人、换个项目是否仍然成立？」若成立，补事实或删除。

## 5. 删除无价值过程

默认删除：

- 工具安装、命令、工程测试次数。
- 文件搬运、目录清理和内部操作流水。
- 「投入很多」「持续努力」等无法帮助决策的描述。

保留：

- 最终结果和业务影响。
- 数据及可信证据。
- 未完成原因、风险和处理动作。
- 团队需要知道的依赖与协同。

## 6. 数据审计

- 周期是否一致？
- 合计数是否重复统计跨平台同一内容？
- 是否区分独立选题数与发布条次？
- 删除或下架内容的统计口径是否已说明？
- 累计账号数据是否被误写为本周新增？
- 进线和成交是否被错误归因到单条内容？
- 模糊截图中的数字是否被猜测？

## 7. 行动价值

每个重要判断后检查：

- 是否明确继续、调整、停止或补充验证？
- 本周任务是否有目标和指标/交付物？
- 协同请求是否说明对象、资源和期望时间？

内部为每个重要条目判断「仅供知悉、需要决策、需要支援、已闭环」。除非上一周格式已有此标签，否则不在正文显示标签，只用来决定条目位置和是否进入协同事项。

## 8. 风险分流

- 是否识别已发生的延期、未达标和数据下滑，以及正在变成问题的卡住、等待他人和资源缺口？
- 普通风险是否进入上一周已有的「问题与风险」章节？
- 会影响他人排期、对外承诺、资源安排，或可能被第三方先知道的事，是否同时准备了单独沟通文本？
- 单独沟通文本是否说清事实、影响、可选方案、推荐选择和最晚决策时间？
- 是否用具体日期、数字和客观约束代替「略有滞后」「最近事情较多」？
- 是否避免点名甩锅和泛化自责，并把责任指向具体的补救动作？

## 审核输出

不要单独生成冗长审核报告。直接修改初稿，并在确认消息里最多列出：

- 已收紧的关键表达。
- 仍需用户拍板的事实或口径。
- 即将写入的飞书标题。
