Hello，大家好。今天我们来聊一个在开发圈已经越来越热，但是我觉得还没有被足够重视的一个事情，叫作 MCP，全称呢就是 Model Context Protocol，模型上下文协议。

你可能在各个公众号里面或者科普视频里面看到，他们把 MCP 比作 USB-C 这个比较通用的数据线接口，听起来很通俗易懂，对吧？但其实我觉得这个比喻有点肤浅，反而掩盖了 MCP 真正的颠覆性价值。

MCP 的真正应用价值，我觉得它不单单只是便利，而是从根本上去重构了 AI 的整个应用架构，真正地把 AI 从 Chatbot 这个阶段推进到了 Agentic AI 这个阶段。接下来呢，我还是会从什么是 MCP、为什么 MCP 这么有用，以及我们怎么去用 MCP 这三个维度，给大家讲明白。

我们先从定义说起。MCP 呢，它不是一个工具，不是一个应用，不是一个 API、SDK，也不是一个产品，而是一个协议。它的目标呢，是希望任何一个 AI 模型，比如 GPT、比如 Claude，能够以一个统一的方式去访问资源和工具。

举个更直观的比喻，HTTP 这个我相信大家都知道，它是网页和服务器的一个通信协议，而 MCP 呢，就是模型和外部世界的一个通信协议。

那模型需要通信，或者更直观地说，需要交互什么呢？就是任何你希望模型知道、能用、能调的内容。具体呢，就是从我刚提到的两个层面，一个就是资源，第二就是工具。数据资源呢，就包括数据库、API、第三方的 SaaS 等等。可执行的工具呢就更多了，比如创建日历、发邮件、执行命令、远程控制等等等等。这些资源和工具，就是真正能够去让大模型变得真正有用的上下文和能力。

OK，接下来我们来讲为什么我们需要 MCP。过去我们经历了三个阶段。

第一个阶段呢，就是 AI 模型单独使用的阶段。最初的 GPT、Claude，本质上就是基于海量数据训练的一个下一个词的预测器，我们叫作 Next Token Prediction。本质上呢，我拿到用户的输入，然后通过一个词一个词最大概率的方式去给到用户输出。它们确实很聪明，但也经常会胡说八道，也就是我之前提到的幻觉，因为它们是孤立存在的，没有接收任何的外部信息。

OK，接下来呢，就是进化到第二阶段，就是上下文输入给大模型。比如我们现在用的 GPT 或者 DeepSeek 都有一个 Web 选项，这个就是网络的上下文。AI 编程模型 Cursor 呢，就相当于我们的模型加上我们的代码。接下来呢，就相当于我们的 AI 模型加上各种 Google 的日历、文档。所以它们不再是一个 Chatbot，它们集成了各种的工具和信息，这就是它们能够去提供很炫酷的产品和服务的原因。

但到了 LLM 加 Context 这个阶段，你需要去调用 API、调用数据、更新文件，那情况就变了。为什么呢？你相当于遇到了一个 N 乘以 M 的大规模集成问题。比如你有 N 个 AI 应用，有 M 个外部的服务、工具和资源，那我们就有 N 乘以 M 个连接。每个连接都需要去定制代码、去写特定性的服务、去处理权限、去管理格式、保证足够的兼容性，最终呢，就会导致整个系统非常复杂，极难去维护，极难去规模化。

这就相当于你抽屉里装满了各种各样的充电器，有 Type-C 的、以前苹果的、安卓的，混乱不堪。

OK，所以我们就迎来了第三个阶段，也就是 MCP。它提供了一个统一的协议，只要你实现了 MCP，你就能够即插即用地去连接 AI 和整个世界。

OK，接下来我们再来讲一下 MCP 是怎么去工作的。我们先从架构讲起。你可以把它理解为一条标准化的数据和能力调用通路，也就是用户输入 Prompt，然后给到 MCP Client，MCP Client 呢给到 MCP Server，最后呢跟我们的资源和可调用的工具去对接。

MCP Client 呢，就相当于你的 AI 应用，包括桌面助手、包括 Bot、包括各种的 Agent。它的角色是去把用户输入的一些含糊不清的自然语言，转换成一个明确的意图，告诉系统：「我想做一件事情，我要去发邮件，我要去写一个数据库，我要去写一段代码。」

这些请求呢，会被发送给 MCP Server，也就是能力适配器。MCP Server 就负责去和外部的系统通信，比如各种邮箱、各种日历、GitHub 等等，并且会声明出它提供的资源或者功能。

比如一个 Gmail 的 MCP Server 呢，它可以去发送邮件、接收邮件、写邮件；一个 Calendar Server 呢，它可以去设置日历、设置通知；一个 GitHub Server 呢，可能会执行代码、审查代码、编写代码等等。这些 Server 都实现了一个统一的协议，支持通过 HTTP、通过 JSON，或者通过本地输入输出的方式，去跟 MCP 的 Client 进行通信。

我们来举一个更加实际的例子。比如我发出请求说：「请帮我约张老师下周一起去喝咖啡，并发一个邮件给他提醒。」这个请求其实包含两个目标。第一个呢，是去找到我和张老师在周二的时候都空闲的一个时间段；第二个呢，是去创建一个日程提醒并发送通知。

那么 AI 应用作为一个 MCP Client 呢，会先向系统中已经注册的 MCP Server 去查询它的能力列表，比如是不是可以去访问日历，是不是有权限去发邮件，是不是能够去获取到联系人的信息。然后这些能力的声明和用户的请求，一并交给大语言模型去进行处理。

模型基于给定的上下文呢，去判断应该怎么整合现在的工具，去完成我们要达到的任务。比如它决策后发现，第一步，先从 Calendar Server 里面去找到我和张老师可用的一个时间段；第二步呢，决定最终的会议时间；第三步呢，调用 Email Server 去发送邮件；第四步呢，可能还会去提问用户，我是不是该去确定一个会议地点，是不是还要去发邮件给其他人。

整个流程非常标准、清晰，逻辑也是闭环的。最关键是，你不需要去为每一个流程写死一个逻辑，模型也不需要去提前训练，才知道每一个 API。只要 MCP Server 有这个能力的声明，模型就能够去动态地发现、调用、执行。

OK，接下来呢，我来讲一下 MCP 能够带来的一个方式转变。我觉得主要归到三个核心的优势：第一个是可插拔性，Pluggable；第二个呢，是可发现性；第三个呢，是可组合性。

你可以把每一个 MCP Server 理解成一个功能模块，就像拼积木一样去接进系统。在未来你要去构建 AI 应用的时候，你只需要去注册你所需要的 MCP Server，模型呢，就能够立刻地去接入这些能力，就像插入了一个插件，获得一个新的技能。

而你呢，就不需要手把手去教模型调用哪个 API、发什么请求、传什么参数。你只需要去告诉它，这里有一组工具和资源，它们能够去做什么，已经给它说明白了，那模型呢就能够自行去判断这个工具和资源是不是有用的，并掌握如何去使用这些有用的工具和资源。

所以最后总结来看，MCP 不仅仅是一个方便的工具接入接口，它是一个全新的协议标准，正在重构 AI 和世界的交互方式。它让我们从使用 AI，迈向了让 AI 使用系统；从只是单纯地生成文字、生成图像，转化成了调度执行。

有了 MCP 呢，你也不用去担心 AI 怎么去接、怎么去做、怎么去集成。你只需要去清晰表达你想要让 AI 去完成什么任务，其余的 AI 就能够自己去搞定了。这个也正是我们希望的 AI Agent 的一个核心本质，也是 MCP 带来的一个深刻变革。
