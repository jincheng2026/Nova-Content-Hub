# 创作协作与审稿

## 1. 回读后再回应

用户说改完了、看一下、继续改稿时重新读取 context：当前正文、确认 hash、所有相关批注、建议接受/拒绝状态、关联任务中的上一稿及反馈。若受控上下文没有可比较的底稿或历史，明确无法完整判断手改差异，不反推修改原因或扫描无关聊天。

能取得前后稿时按段落列变更：原句、新句、作者是用户还是 AI、直接理由或 AI 归纳。整段重写只记录整段及原因，不用大量逐字条目掩盖重要取舍。底层事务存在不等于已经有可用的改稿日志；只记录本轮实际读到的证据。

逐条回应未处理批注，说明建议怎样处理或为何保留；用户拒绝过的建议不换个措辞重复推回。涉及当前任务之外的制作/发布操作只记录交接，不借批注扩大任务权限。

## 2. 形成可定位建议

每条建议解决一个具体问题，并提供当前正文中准确的原句、建议替换、理由和依据。引用唯一时才适合一键替换；原句重复时扩大到足以唯一定位的相邻上下文，仍有歧义就改为批注说明位置。

遵守当前产物合同的 suggestions/annotations 字段：使用刚读取的 bodyHash，quote 精确对应原文，状态为 pending/open。如果新合同支持段落或位置锚点，按其规定填真实锚点；不要自行添加字段或猜 offset。

建议按原文顺序组织，一段通常保留三到四条最有影响的修改，区分事实问题、理解障碍、口播或可选表达，不机械凑数。删整句用合同允许的空 replacement 表达；不得把删除意见变成无引用的全文替换。

若建议属于同一轮互斥方案，说明只能选一项；两条范围重叠时合并或注明依赖。不要借调整 hash 让旧建议绕过用户已改的原句。页面能力按实际说明，skill 提交结构化建议不代表已经实现贴句显示。

## 3. 轻量审稿

只在本轮审稿/完整稿自检范围内检查，不新增独立发布前评审页面：

- 观众是否能说出主要收获，正文是否兑现开头承诺。
- 原文是否自然可读；真实试读记录与 AI 静默检查分开。
- 数字、能力、第一人称故事和因果是否有可回查来源；可变产品事实需按当前可靠来源核对。
- 教程关键操作、交付文件和入口是否真实可用；未实测处保留状态。
- 平台和用户的发布边界是否满足；需要核实当前平台规则时查官方资料，不能把历史私人规则当现行政策。

结果用“当前范围未发现阻断项”“需修改后复核”或“存在明确阻断项”，说明检查覆盖；必要修改集中在最多三项关键问题。已通过的稿不重新发散出全新叙事。审稿不代表平台合规、真实拍摄或发布成功已经验收。

## 4. 提交并保留证据

建议/批注可交 analysis 等合同支持的 artifact.data；正文改写交独立 draft，避免同一 artifact 同时夹带正文和建议导致采用语义混乱。回应、理由和变更证据在 text 完整呈现。

用户选择仍由工作台显式保存。提交前再核对正文 hash；变化则回读受影响部分并重做建议。用户反馈按 [反馈与知识](feedback-method.md) 一起交本任务产物，未采纳的 AI 建议不当用户偏好。

完成条件：每条建议可准确定位当前原句，批注有回应，旧稿不会覆盖新稿，产物回执可读；没有证据的确认、试读和采用状态没有被编造。
