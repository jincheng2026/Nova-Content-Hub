Hello，各位，最近 Vibe Coding 特别火，但很多朋友都在反映一个问题：我通过 Vibe Coding，项目推得特别快，但是越往后代码越乱，慢慢变成一个什么？变成屎山。然后你越改就越差，最后牵一发而动全身，整个项目直接崩盘。

问题不在于 AI 强还是不强，问题在于 Vibe Coding 并不是说，我把这个活直接丢给 AI，我就完事了，等它执行就可以了。而是你还是需要构建一套工程流程，去驾驭这个 AI。

所以今天我就给大家讲解一套标准的工作流，把 Vibe Coding 的工作流程讲透。这里我把它分成了开发前的九个步骤和开发中的五个关键点。你可以自己去试一下，项目的成功率会高很多。

好，那首先我先来讲开发前的九个准备步骤。我把它定义成，用 AI 写第一行代码之前，你就需要用这几个步骤把地基打好。

所以这九步，我分成了三个阶段。第一个阶段叫作定图纸，第二个阶段叫打地基，第三个阶段叫立规矩。每一个阶段中间都包含三个小步骤。

我们先说定图纸。定图纸的第一个步骤，就是先别写代码。先干嘛？先去聊需求。就好像你跟朋友聊天一样，把痛点、目标用户、使用场景和你理想中的核心功能全部讲给 AI。这个时候你不用追求严谨，追求信息量。

OK，定完需求以后，步骤二就是把这个需求整理成一份 PRD 文档。但虽然写成 PRD 文档，你要去做一个验收标准。比如你可以让 AI 输出一份比较结构化的 PRD 文档，它中间包括功能列表、用户流程、页面清单。

然后重点来了，每个功能你之后都要补一句：到底做到什么程度才算完成？标准一定要定好。比如说，登录成功不是一句话，要说清楚登录失败提示是什么，会不会锁定，成功以后会跳到哪里。如果你没有验收标准，AI 一定会写得越来越发散。

好，那步骤三就是提前定好视觉以及页面框架。在这里你可以去找两到三个参考网站，或者让 AI 给出几种风格方案。你需要决定，比如我的导航栏怎么放，页面有哪些区块，然后整体我想要的气质是简约的，还是比如豪华风。这一步就是为了后面不让 AI 一边写功能，一边把 UI 推倒重来。

好，那等我们把图纸定完以后，我们就可以进入第二步，把地基打好。

OK，地基也是分成三步。第一步，你要明确项目的边界和非功能需求。针对这个，我建议你回答自己三个问题：第一，这是本地自用，还是要上线公开？第二，有没有用户数据、支付、隐私、合规？第三，性能和成本有没有上限？

这个就叫作非功能需求：安全、性能、可用性、成本。你这四个不写清楚，我觉得后面一定会返工。

OK，然后再讲步骤五，我们要锁定技术栈。但是原则并不是越主流越好，而是越可验证越好。主流技术通常更稳，因为资料多、工具链成熟，AI 也不容易瞎编。但更关键的是，你选的这个技术除了主流以外，还有更多社区材料、官方文档或者清晰示例，然后能跑测试、能进 CI。

所以一句话总结，就是你不用追求特别潮，比如说某一个新的框架出来，你就立刻用它。而是要追求可控，资料更多。

步骤六就是让 AI 出一个轻量化架构。这个草案不要一次就给它写死，说它出这个架构草案以后就不要变了。你要它输出，比如目录结构怎么分层、核心模块有哪些、数据模型到底长什么样、哪些逻辑必须要在服务端。

而且注意，这个是一个草案，我不会把它定义成比如宪法这样的东西。你要允许它能够持续迭代，但是每次迭代都需要记录原因。

好，那讲完了地基的三个步骤以后，接下来就到最后的，我们要把规矩立好。

规矩立好，首先我们现在和 Agent 或者大模型交互，都会用一个文档。所以你需要把 PRD、架构、当前状态写成项目根目录的三个文本，固化成文本。比如你可以写 PRD.md，然后 ARCHITECTURE.md 描述架构，还有 PROJECT.md 描述现在的项目阶段，比如说做到哪一步、有哪些已知问题、下一步要干嘛。

这三份就是 AI 的全局上下文。重点就是，每次大的改动，这三份必须同步更新，否则 AI 就会按照旧的世界观写新代码。

好，然后到步骤八，就是要定开发规范和建参考资料了，让 AI 有照着抄的标准。比如必须要用 TypeScript，必须遵守组件的命名规则，还有文件大小上限。另外你还可以再建一个像 reference 这样的文件夹，放你认可的按钮、表单、弹窗的标准实现。

好，那规矩的最后一步，就是写第一行代码的时候，你需要把 Git 和质量的闸门拉起来。

Git 大家都知道，或者不知道的，我给大家介绍一下，它是一个代码版本管理工具。所以我定义它就是一个安全带。比如说某个代码通过 AI 写着写着，直接写飞了，那可以通过 Git 一键回溯到以前最好的代码。同时，通过多个分支开发，能够做不同特性的并行开发，也不用担心会有冲突。

OK，那现在我们的九个步骤都定义好了，接下来我们就开始讲开发中的五个核心关键点。这里你需要记住一句话，就是你负责边界和验收，AI 负责体力活。

所以根据这个大原则，第一个关键点就是，你要坚守小步迭代的 MVP 法则。你不要一口气让 AI 写一大堆，而是一次只做一个可验证的小切片。比如说，从页面能打开，到能提交表单，到服务端保存，到权限校验，到列表展示。你每完成一个能跑通的切片，就跑测试、过 Lint，然后 Git 提交一次。

OK，关键点二就是人类必须介入。这个很简单，因为我们需要做模块拆分。你不允许所有代码都放到同一个文件里面。虽然我们前面看得很爽，但后面你通过这个文件去找某一个功能，会特别崩溃。

好，第三个关键点，限制 AI 权限，禁止 AI 做主。你可以用状态摘要去管理上下文。比如说你让它修一个按钮，它可能顺便重写整个页面。所以每次任务结尾，你可以加一句提示：只改我点名的文件和范围，不要顺手重构，不要改 UI 风格，不要改无关逻辑。

好，第四个关键点，就是要守住安全底线。这个不是口号，而是清单。因为 AI 写代码往往只求能跑，不会默认安全。所以你至少要盯住这些底线，比如 API Key 永远不要进前端，因为很容易被人 Hack 出来；然后不要进仓库，要用环境变量和服务端调用。另外，服务端要做鉴权和授权校验，不能信任前端等等。

OK，那最后一个关键点，就是你要科学地应对报错。如果两次没有新增证据，就停掉，先缩小问题面。报错的时候，你可以把错误信息给 AI 去修一次。你第一次做一次，然后 AI 修了一次。如果连续两次都没有新增一些证据，或者有所提升，只是在猜，那你就必须停掉。

这些动作有三步。第一个，你要做最小复现，把问题缩到最小输入。第二个，加日志、加断点，然后打印关键变量和分支。第三个，写一个小测试，把关键行为锁住，然后再让 AI 基于这些证据去修。

那实在不行，就只能借助 Git，回滚到上一个稳定点，别让它再乱改和扩大损失。

OK，所以我最后总结一下。我们现在列了开发前九个步骤和开发中的五个关键点。这九个步骤告诉你要做什么，以及怎么做。开发中的五个关键点，像小步迭代、主动拆分、限制 AI 的行为、守住安全底线、科学应对报错，决定了你的项目到底能不能真正落地、存活。

OK，那最后希望这套方法论能够帮你顺利交付自己的产品。
