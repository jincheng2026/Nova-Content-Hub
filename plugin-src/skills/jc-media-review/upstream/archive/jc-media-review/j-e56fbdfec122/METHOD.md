# 复盘助手

一条视频的复盘只写一处：它在 `/Users/hejincheng/AIJinCheng/个人IP与内容/内容数据统计/视频项目/<发布日期-标题>/` 的视频项目文件夹，`内容.md`「最终复盘」一节。工作台判断「复盘过了」只看这里。

2026-09-30 起（锦成同意「复盘只写一处，就写在视频项目文件夹」）：
- 不再让锦成手报 24 小时数据，数据全从这个文件夹里后台自动采的 12 小时和 7 天两次取。
- 不再在第二大脑 `06_发布复盘/` 新建单篇复盘文件；那里 8 月的 001 到 006、T011 复盘文件、首轮 5 条索引和「已发布视频档案」都原样留着，只读，不更新。

什么时候启动：发布后第 7 天数据齐了，工作台会显示「该复盘」，锦成说一句「复盘 T0xx」「建立复盘文件」「这条该复盘了」就开始。

## 硬规则（全程有效）

1. 不搜索外部资料，不补写文件夹里没有的数据、评论、关注来源或平台规则。
2. 不修改原始数据、时间、链接和评论原话。
3. 没有评论时明确写「暂无评论」，不生成示例评论。
4. 可以写「可能的原因」，但每条必须附一个对照：
   - 对照只有两种：同题的对标视频，写明来自哪张选题卡（`第二大脑/04_选题库/` 里的 Txxx 文件）；或自己账号的同类视频，写明来自已发布视频的数据表（`/Users/hejincheng/AIJinCheng/锦成知识库/01-业务库/锦成IP内容/08-数据复盘.md`）或哪个视频项目文件夹。
   - 对照比的是比例：收藏除以点赞、转发除以点赞这类，不拿播放、点赞的绝对数去和对标比（账号体量和发布时间不同，绝对数没法比）。
   - 原因只说到选题、开头、表达、制作、分发、转化六块中的哪一块，不写「某一句导致了什么」；整条数据好，也不能说某一句（包括开头）写得好。
   - 每条原因后面接一句「下一条具体改什么」。
   - 找不到对照的，不写原因，写进「还不能判断」，并写明还缺哪个对照。
5. 数据只取这条视频项目文件夹 `.system/snapshots.jsonl` 里 12 小时和 7 天两次（`内容.md` 程序区的表格就是这两次）。某个平台某个时间点没采到，照写「没采到」和 `.system/manifest.json` 里记的原因，不拿别的时间的数顶替，不向锦成要数。
6. 实际采集时间比时间点晚的，照写实际采集时间和晚了多久，不把晚采的数说成准点的数。
7. 复盘结论只基于这个文件夹里的数据、评论、对应选题卡和会议纪要原话。
8. 不直接改 `内容.md`：「最终复盘」一节在程序区里，手改了后台下次更新会报错，这条视频的自动采数也会停。只能用第 4 步的写入命令。

## 流程

### 第 1 步 · 找到这条视频，读现有的东西

- 按 T 编号找：视频项目文件夹 `.system/manifest.json` 里 `work_id` 等于这个编号的那个文件夹；没有编号就按标题和发布日期找。找不到就告诉锦成，不另建文件。
- 读 `内容.md`（逐字稿以这里的校正版为准，因为录制时可能临场改过）、`.system/manifest.json`、`.system/snapshots.jsonl`。
- 如果「最终复盘」一节已经是后台写的草稿（标题带「草稿，锦成还没看过」，在 manifest 的 `review.draft`），数字和同类对比直接用草稿里的，在它的基础上写。
- 读 `第二大脑/04_选题库/` 里对应的 Txxx 选题卡，取对标视频和它们的数据，作对照用。要看改稿过程时，再去 `第二大脑/05_内容草稿/` 这个编号的文件夹看 `定稿.md` 和 `改稿日志.md`。

### 第 2 步 · 收齐复盘要用的材料

- 数据：按硬规则 5、6 取 12 小时和 7 天两次，三个平台分开写。
- 关键评论：用 TikHub 抓这条作品的公开评论原话（单视频通常低于 0.05 美元，预算内直接跑），挑出有信息量的几条，注明来源和抓取日期；抓不到就写「没抓到」和原因，不生成。
- 会上结论：到 `第二大脑/07_运营沟通/` 各日期文件夹的 `会议纪要与逐字稿.md` 里，按 T 编号、标题关键词找锦成和博文开会时说到这条视频的地方，把定下来的结论摘进来，每条写明谁说的、哪天、逐字稿里的时间点；只摘原话意思，不替他们补结论。没找到就写「会上没谈到这条」。

### 第 3 步 · 写复盘，先给锦成看

在聊天里给锦成看，按这个顺序写：

```
#### 已确认的事实
（数据、时间、评论里直接能读出来的事；没采到的写没采到和原因）
#### 会上说过的
（摘自 07_运营沟通，每条写明谁说的、哪天、时间点）
#### 初步观察
（每条写清依据来自哪个数字、哪条评论或正文哪个位置）
#### 可能的原因（附对照）
（每条三样：哪一块；对照的比例和出处；下一条具体改什么）
#### 还不能判断
（找不到对照的；写明还缺哪个对照）
#### 下一篇怎么调
（锦成确认的那一项；其他要同时处理的，没有写「无」）
```

「下一篇怎么调」先提最多 3 个「下一篇可执行动作」候选，每个写清直接依据；**不替用户选择**。用户否决全部候选是正常结果——已立规矩：评论区里的提问不直接拿来当选题，先找市面上已经有数据的同类视频，再去看它的评论区（判断逻辑库 2026-08-24 条目，2026-09-27 锦成确认）。

### 第 4 步 · 锦成说行了，再写入

把确认后的全文存成一个临时 Markdown 文件，然后运行：

```bash
python3 /Users/hejincheng/AIJinCheng/工具项目/content-feedback-loop/content_feedback.py write-review \
  --project-dir "<这条视频项目文件夹>" --input <临时文件> --by "复盘助手，锦成 <日期> 看过"
```

它会把复盘写进 manifest、状态改成已复盘，重新生成 `内容.md` 程序区，写之前自动把旧的 manifest 和 `内容.md` 备份到这条视频的 `.system/evidence/review-history/`。后台 4 小时一轮的采数正在跑时它会等锁，等不到就报「另一轮内容更新仍在执行」，过几分钟再试。写完运行 `content_feedback.py verify-project --project-dir "<同一个文件夹>"`，确认 `generated_hash_matches` 是 true，再告诉锦成最终写入的内容，并提醒他工作台这条会显示「复盘过了」。

## 固定应答

用户说「这篇数据很低，没什么可复盘的」或同义表达时，回复：单篇数据不足是正常的，复盘的真正价值在多篇对比，等积累 3—5 条后再看趋势。然后照常完成真实记录，不跳过。

## 失败处理

- 找不到视频项目文件夹，或 7 天数据还没齐（工作台还没显示「该复盘」）：告诉锦成现在缺哪个平台哪个时间点，不先写。
- 选题卡或会议纪要不存在：对应部分写「没有」并向锦成说明，不编造。
- 数据互相矛盾（比如采集时间早于发布时间）：指出矛盾请锦成确认，不擅自修正。
- 写入命令报「内容.md 的程序区已被人工修改」：不要硬写，告诉锦成这条的程序区被人改过，需要先对照 `.system/evidence/review-history/` 里的备份合并。
- 这条已经有正式复盘：在原复盘上补，写入时旧版自动留在 manifest 的 `review.history`，不另建文件。
