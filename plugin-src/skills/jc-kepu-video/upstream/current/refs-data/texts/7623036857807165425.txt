今天我们来讲一个最近特别火的词，叫作 Harness Engineering。

首先，我们先看一看这个词到底是什么意思。我们给大家做一个比方。想象你有一匹马，马很有力量，但是它有力量本身也不代表有用。真正让马的力量变得可以使用的是什么呢？是套在它身上的那套马具，像缰绳、马鞍等等，这个统称就是 Harness。

OK，那对于大语言模型来说，现在 Harness Engineering 为什么这么火呢？因为 LLM 也是一样，模型很有能力，可以说是基本上上知天文、下知地理，但是模型有能力，不代表它能够给出一个好的输出。

所以 Harness Engineering 的直观比方，就是研究怎么在这个模型外面套一层好的、像马具一样的东西，让模型的能力可以被稳定地、可重复地驾驭。而且 Harness Engineering 不再是单单把 Prompt 提升这样的一个概念，它比 Prompt 大一个量级。

首先，要理解 Harness Engineering 这个概念，我们先要知道 LLM 到底有哪些结构性的缺陷。

首先我们知道，模型本身是无状态的，每次对话结束，它什么都不记得。它无法主动操控外部世界，只能生成文字。同时，它有上下文限制，不能无限制地处理信息。而更关键的是，它的输出是概率性的，同样的输入可能会产生不同的输出，而且你无法事先保证哪一次是对的。

OK，你看我刚刚列了大概四五个这样的缺点，而且这些都不是 Bug，这本身就是模型自己的基本性质。所以 Harness 要做的，就是在这些性质的基础上建造一套系统，让模型可以完成原本无法独立完成的任务。

我用一个更简单的类比，你可以理解为模型是一个引擎，Harness 是外面的这辆车。你看，如果我们的引擎再牛，比如说八缸、十二缸，但是你没有变速箱、没有刹车、没有仪表盘，那这个车也没办法上路。

好，那讲完了 Harness 对于模型的作用之后，我们再讲一讲 Harness 到底包含哪几个结构。它不是一个具体工具，而是围绕模型构建的几类基础设施的总称，核心一共有四层。

第一层，记忆层。这个主要解决模型无状态的问题。模型本身不记得上一次对话说了什么，也不知道你的项目有什么规范。记忆层用文件系统做持久化，把需要模型知道的东西写下来，结构化存放，让模型每次工作都能检索到正确的背景信息。

在代码场景里面，这个通常就是 CLAUDE.md 或者 AGENTS.md 这样的文档。这两个也不叫百科全书，而是一张导航地图，只告诉 Agent 最关键的约束和规则。

好，那整理完记忆层以后，我们接下来就是执行层。这里解决模型只能生成文字的问题。像 Bash、代码执行、浏览器的操控、API 调用，这些能力让模型真的从“我只是给你讲一些话”，变成“我真的去做这个事情”。

同时，Harness 提供这样的沙箱环境，保持它的试错成本为零。Agent 在隔离的工作区里面可以大胆改动，改坏了直接丢掉，不影响主分支。

OK，那第三个叫作反馈层。反馈层解决的就是模型输出不可靠的问题，这个是整个 Harness 框架里面最核心的部分。

你看，像测试、Lint、CI 流水线，这些工具构成了对模型产出的确定性验证机制。模型生成代码，测试立刻跑一遍。不通过，那就自动打回重试；通过了，才会进入下一步。反馈的速度从人工 Review 的小时级缩短到了秒级。

这个回路能够闭合，根本原因就在于代码有一种特殊性质：生成虽然是有概率性的，但是验证是确定性的。所以你不需要模型每次都对，你只需要有足够好的验证手段就够了。

第四层就是编排层，主要解决复杂任务的拆解问题。你看，我们一个大的任务，不可能都交给一个模型去做。我可能会拆成几个并行的子任务，多个 Agent 分工协作，中间可能会有 Hook 和中间件协调状态。这些让系统可以处理远超单次对话能力上限的工程任务。

OK，以上就是整个 Harness 的四个组成框架。

那我们再聊一下，为什么代码领域是突破口。你看，LLM 在很多领域都有应用，但 Harness Engineering 在代码场景发展得最快、最系统。原因就在于一个不对称性，就是我刚提到的，代码生成是概率性的，但是验证是确定性的。

编译器不会因为你今天心情好，就放过一个语法错误。测试也不会因为你的态度端正，就假装通过。这种确定性让反馈回路在代码领域可以做到完全自动化。

相比之下，我们写一篇文章到底对不对，我们做一个影视内容，看它到底好不好，这个问题很难用机器自动判断。你看，设计一张海报好不好，那更难，对吧？但这段代码能不能通过一百个测试用例，可以，而且可能在三十秒内就能给你一个答案。

所以这个性质意味着什么？Agent 在代码领域犯错了，系统可以立刻打回；Agent 修正以后，系统可以再次验证。这种循环可以高速运转，不需要人盯着。

但注意，这里有一个容易忽略的前提，就是验证基础设施本身要足够好。没有测试，拿什么验证？没有这种 Lint 规则，架构约束怎么自动执行？

过去，这些工程实践被称为最佳实践，大家都觉得重要，但是可以拖。那 Agent 时代，拖的代价完全不同。一个没有约束的 Agent，会以机器速度、全天候地在每一个 PR 里面重复同样的错误。因为没有写下来的规矩，它自己永远意识不到，或者永远也学不会。

好，那抛出了理论之后，我们在落地上其实也有几个反复被验证的设计模式。

第一个就是之前那个 Skill 的概念，叫作渐进式信息披露。也就是不要把所有文档一次性喂给 Agent。好的做法是写一份精准的入口文档，只告诉 Agent 最关键的导航信息，详细规则按照模块分类存放，Agent 自动按照当前任务按需加载。这样做既避免了上下文窗口的压力，也迫使你把规范整理得更加清晰。

好，第二个叫作沙箱隔离。每个 Agent 的任务在独立的工作区里执行，互不干扰，坏了直接丢弃。这让 Agent 可以大胆试错，失败的成本接近于零。

第三个就是仓库是真理来源。架构规范、质量标准、命名约定，全部都写进代码仓库。不要靠口头传达，不要靠 Slack 消息。Agent 读仓库，就能够获取所需要的上下文。

好，接下来还有机械化地执行约束。像架构约束，我们不用靠 Code Review 里面的文字建议来传达，而是编码进 Lint 规则。违反了就自动编译不过，PR 就不让它合进去。

所以你看，人是心软的，可以被说服，但规则不会。这个是约束真正有效的唯一方式。

OK，那以上就是 Harness Engineering 从概念，到核心组成，再到后面关键点的整个解读。

最后，我还是想聊一聊，为什么 Harness Engineering 值得认真对待。从我的角度，就是当 AI Agent 承担越来越多代码生成工作的时候，我们人，或者我们工程师，核心竞争力就要从“我能够写出什么”，转向“我能够评估什么”，以及更深一层，“我能够设计什么样的系统，让正确的代码可以被可靠地生成和验证”。

这里也不是说写代码能力不重要，而是说，能够清晰地定义问题、建立有效的验证机制、把团队的架构直觉转化成可执行规则的工程师，与不具备这些能力的工程师，将产生越来越大的生产力差距。

所以 Harness Engineering 说到底，就是关于怎么把人的判断力固化成系统，让它不再依赖于某一次对话，不再依赖于某一个人在场，而是变成一个可以持续运转的基础设施工具。

所以也希望大家以后自己好好了解一下这个概念，以及它在你的领域是不是能够产出一些帮助你的东西。
