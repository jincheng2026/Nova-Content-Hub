Hello，各位，我相信大家和大模型对话的时候都会有这样的体验：花了四个小时和 Claude 调试了一个 Bug，好不容易解决了，第二天早上打开一个新的对话，Claude 对于昨天的事情可以说是一无所知。你得从头解释自己的项目结构，从头提醒它构建命令，这个体验真的是烂透了。

2 月 27 号，Anthropic 在 Claude Code v2.1.59 这个版本正式上线了一个功能，叫作 Auto Memory，就是为了解决这个遗忘的问题。但是它解决得好还是不好？有没有新的坑？值不值得大家现在就打开？这个大家可能都是存疑的。

所以今天我就来深度拆解 Auto Memory 自动记忆这个机制，把这些问题给大家说清楚。

首先，我先给大家讲清楚这个核心概念：Auto Memory 到底是一个什么东西？Claude Code 里面的记忆不是一个东西，而是两个。记忆系统其实分了两个板块。

第一个叫作 CLAUDE.md，这个是我们写的，里面包含了我们之前有写过的编码规范、构建命令、团队约定。还有一个板块就是 Auto Memory，这个是 Claude 自己写的，这里包含了调试经验、项目模式以及工作习惯。

比如，项目用了什么构建命令，测试怎么跑，你踩过什么坑，包括你偏好什么风格，Claude 都会把这些笔记写进本地的 Markdown 文件。下次开新对话的时候，它就会自动加载这个文件。

这里一定要注意我刚说的那个词，叫作自动，也就是 Auto。你不需要告诉它“你把这个给记住”，然后你也不需要手动维护这个 Markdown 文件。你只需要正常工作，它自己会决定什么值得记、怎么去记。这个就是 Auto Memory 的核心卖点，也是它最大的争议来源。为什么会有争议呢？我们后面再讲，我们先讲它怎么运作。

首先，我们先搞清楚这个 MEMORY.md 到底是存在哪里。它其实存在你的 `~/.claude` 根目录下，然后 `projects` 里面对应某个项目的 `memory` 文件夹。`memory` 里面包含了四个标准的 Markdown 文件。

首先就是 MEMORY.md，这个是主入口，它主要做的是索引所有文件。第二个就是 debugging.md，这个顾名思义就是一些调试笔记。另外还有 api-conventions.md，这个是 API 的设计决策，包括 build-patterns.md，这个是构建模式。

每个项目都有自己的独立记忆目录，这个路径是从你的仓库根目录推导出来的。OK，那重点来了，同一个仓库的所有子目录共享的是同一份记忆。

MEMORY.md 就是核心，每次你启动一个新的对话，Claude Code 会自动加载这个文件的前 200 行，然后加载到你的系统提示词里面。另外一定要注意，200 行是一个硬上限，超出的部分不会加载。

OK，那你可能会有些好奇，为什么会是 200 行？其实我自己一开始也比较好奇，后来大致看了一下，它其实就是 Claude 的设计。它逼着 Claude 这个模型把 MEMORY.md 保持得很精简，像一个目录，而不是一个百科全书。详细内容会拆到 debugging.md、api-conventions.md 这样的主题文件里面，Claude 需要的时候再按需读取，前提是它知道自己需要。

OK，接下来我们再讲 Auto Memory 的三种管理方式。

第一种就是被动模式，什么都不用做。你正常写代码，Claude 就会在工作中自主判断这个是不是值得记，然后把它写进去，你甚至都不用注意到。OK，这个我觉得是最轻的一种模式。

第二种就是主动指示。你直接跟 Claude 说，你要记住我们要用什么、不要用什么，然后记住每次提交代码之前要跑一次 `npm test`。它就会把这些也写进 MEMORY.md。我觉得这是一个比较中度的管理。

第三种就是手动管理。你直接在 Claude Code 里面加上 `/memory` 这样的命令，Claude 就会弹出一个文件选择器，你可以直接打开任何的记忆文件做编辑。里面还有个开关，可以一键关闭或者打开 Auto Memory。手动管理我定义成一个更重度的记忆管理，有点像 Hack 这个代码一样。

OK，我觉得 Auto Memory 不是凭空冒出来的。在它上线之前，开发者社区其实已经喊了很久了。所以我给大家梳理一下这个需求的演变。

在 2025 年 12 月的时候，就有一个 Issue 说，希望不要让 Claude 每次启动都从零开始。你看它说的是“Persistent Memory Between Claude Code Sessions”。然后到 2026 年 1 月，又有一个 Issue 说“Add Automatic Memories Like ChatGPT”，关键词就是 Automatic。然后在 2026 年 2 月，它提出在 Context Window 压缩前主动保存研究成果。

所以，如果我们把这三个 Issue 拼在一起，就能看到一条完整的进化线：第一个就是需要先记住，然后再自动记住、加自动化；那自动记住以后，在关键的时候自动记住。而现在 Auto Memory 走到了第二步，就是能够自动记住，但是第三步我觉得还没完全到，不过已经在路上了。

好，那到这里，整个 Auto Memory 的原理和概念都介绍完了。所以你看，从记住，到自动记住，到关键时刻自动记住，这个大家都能想得到，它也不是一个很革命性的突破，但解决的确实是一个本来就不应该存在的问题：AI 助手不应该每次对话都失忆。

所以从这个角度来说，它只是把一个严重的体验缺陷修补到了及格线。但它修补的方式很聪明：通过存储完全本地、透明，通过分层架构，再通过多级控制。这些设计决策表明了 Anthropic 至少想清楚一件事情：记忆系统最大的问题不是遗忘，是失控。

所以我的建议很简单，就三句话。第一个，打开 Auto Memory，让它跑。第二个，每周花十分钟审查它记录好的 Memory。第三个，像对待一个记忆力终于不为零的新同事一样去对待它。

另外还有一个关键，就是你需要主动地管理 Memory，而不是每次都被动地让 Claude 自己去写、被动地接受。
