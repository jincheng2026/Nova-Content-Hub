- 修正为逐模式精确断言：disabled明确免费体验无需登录；required明确受限内部业务未开放。保留目录、平台、版本、完整性及认证策略断言。

## 集中桌面检查

分别执行 `npm run typecheck:desktop` 与 `npm run test:desktop`，原始日志：[types-01](../verification/production/2026-10-18-unified-types-01.log)、[desktop-01](../verification/production/2026-10-18-unified-desktop-01.log)。

实际源码问题：

1. renderer泛型方法查表调用在新增大量无参IPC后失去输入/输出类型关联。使用明确映射类型保持关联，移除原返回值断言，不使用any、不扩大preload权限。
2. 模板学习卡片使用了已安装Semi版本不支持的`extra`。按本地声明改为`headerExtraContent`。
3. TemplateController构造器参数属性不兼容Node的strip-only加载；改显式readonly字段赋值，保留运行逻辑。native类型检查开启`erasableSyntaxOnly`，使直接由Node加载的源码在类型检查阶段就拒绝此类语法，不到运行用例时才发现。

首轮桌面79项：71通过、8失败；其中7个测试文件未加载，源于上述参数属性语法，不能解释成7个业务流程均已执行失败。

修正后桌面第二轮：[desktop-02](../verification/production/2026-10-18-unified-desktop-02.log)，128项中113通过、15失败。确认其余失败来自过时或不真实的夹具：

- 封面夹具没提供当前必须的助手就绪信息，因而在业务提交前正确被拒绝。显式加入ready助手mock，并新增缺失/禁用助手的拒绝用例，不改生产就绪检查。
- 旧断言未包含“恢复后直接交接”的一次启动；补强为恢复一次、继续两次且同一attempt、不新增尝试。required同步拒绝保留，测试用async包装捕获。
- 旧库夹具把schema5内容/事务仅改库描述为schema4，恢复器正确拒绝伪装。改用真实schema3业务元数据与schema4库描述，恢复校验不放宽。
- macOS临时路径`/var`为系统链接，安全读取与库绑定返回规范路径；测试根目录先realpath，不放宽生产路径检查。

## 完整入口第三轮的模式夹具问题

[source-03](../verification/production/2026-10-18-unified-source-03.log)在原型148项中137通过、11失败。根因是原型测试只将生成配置中的required替换成目标模式；默认配置按一期要求变为disabled后，required用例实际运行了disabled。修正测试加载器同时识别两种合法构建模式，显式断言实际模式等于本用例模式；保留全部授权拒绝断言，不把默认产品模式改回required。完整第四轮结果随后记录。
