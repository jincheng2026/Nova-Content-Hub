# Codex Goal 模式提示词设计

> 这份参考只在用户明确要求生成 Codex `/goal`、Goal 模式提示词、给 Codex 的持续执行目标时读取。长任务、持续执行、后台跑、一直做到完成，只能作为「是否适合 Goal」的判断信号，不能单独触发最终 `/goal` 输出。

## 一句话判断

Goal 模式不是普通 prompt，而是一个「持续执行合同」：

- 普通 prompt：做下一件事，做完回报
- Goal：持续工作，反复检查，直到完成条件成立、预算耗尽、遇到阻塞，或用户暂停

但用户通常写不出这个合同。Goal 分支的工作不是让用户填字段，而是从用户的模糊说法里先代写一版「可审计合同」，再用选项和镜像确认校准。

## 显式触发门

只有用户明确说出以下意图时，才进入 Goal 分支并输出 `/goal`：

- 「帮我写 Codex goal」
- 「把这个任务写成 `/goal`」
- 「生成 Goal 模式提示词」
- 「给 Codex 一个持续执行目标」
- 「让 Codex 自己跑完，不要每轮都让我说继续」

这些词不能单独触发最终 `/goal` 输出：

- 长任务
- 后台跑
- 持续执行
- 一直做
- 直到完成
- 不停地迭代

遇到后一类表达时，只能做两件事：

1. 按普通 Clarifier 流程帮用户澄清需求。
2. 如果确实像持续执行任务，提醒一句「这类任务可以考虑 Goal，是否要我写成 `/goal`？」但在用户明确确认前，不许输出 Goal 模式提示词。

更关键的是：用户通常也不懂编程术语。追问时默认对方没有编程基础、电脑基础。内部可以用 `Scope / Verification / Stop if`，但用户可见的话要翻译成人话：

| 内部字段 | 问用户时怎么说 |
|----------|----------------|
| Objective | 最后你希望 Codex 把什么做完？ |
| Scope | 哪些地方可以动，哪些地方绝对别碰？ |
| First action | 开始前先看什么资料、截图、计划或报错？ |
| Allowed boundary | 只能用哪些材料、文件、工具或账号范围？ |
| Verification | 怎么确认它真的好了？如果你不知道，就让 Codex 先找检查方法 |
| Stop if | 遇到什么情况必须停下来问你？ |
| Budget | 最多让它跑多久，或者最多花多少额度？ |

不要直接问用户「验证命令是什么」「能不能改 schema/API」「benchmark 目标是多少」「CI 怎么跑」。除非用户先用了这些词，否则改成普通说法，比如「有没有一条平时检查项目有没有坏掉的命令？不知道也没关系，让 Codex 自己先找」。

所以 Goal 提示词最重要的不是写得长，而是让 Codex 能回答三个问题：

1. 现在算不算完成？
2. 如果不算，下一步应该继续做什么？
3. 继续做时，哪些输入、工具、文件范围和操作边界不能越过？

## qiaomu 合同层

Goal 分支吸收 `qiaomu-goal-meta-skill` 的核心规则：

- 命令前缀必须保持 `/goal`，正文可以中文；不要写 `/目标`
- 先给可直接复制的推荐执行版，不要先给半填空模板
- 中文用户默认输出中文推荐版；只有用户明确要英文兼容、双语或团队文档时，才附 `Goal Draft (English-compatible)`
- 低风险缺口直接选保守默认值，并用一句话说明「默认选择理由」
- 陌生或专业领域用「发现优先」Goal：先读项目文档、样例数据、现有脚本、官方参考或用户提供材料，再实现最小可验证流程
- 验证必须有证据：命令、日志、截图、文件、API、浏览器检查、样例数据跑通、清单勾选
- 约束写「什么不能变」；边界写「哪里能写、哪里不能碰」
- 迭代必须有上限和换证据规则，不写「一直尝试」「直到满意」
- 完成条件写证据，不写感觉
- 暂停条件必须覆盖凭证、付费、生产数据、删改数据、破坏性操作、法律/医疗/金融判断、版权授权、范围扩大、验证冲突和所有权不清

## 什么时候用 Goal

适合：

- 长时间 coding 任务：迁移、重构、实现计划、清 backlog
- Debug / flaky test：需要复现、修复、验证、继续尝试
- 性能优化：有指标和 benchmark，如 p95、耗时、通过率
- UI / 前端：能用截图、浏览器验证、像素检查确认结果
- 批量整理：有明确输入、输出清单、完成数量
- Prompt / eval 优化：有 eval 命令、目标分数、失败样本

不适合：

- 一次性小改动
- 简单解释、问答、短 review
- 架构 brainstorming、方向探索、主观审美判断
- 没有明确验收证据的「做得更好」「全面优化」「你自己决定」

## Goal 提示词的最小结构

强 Goal 至少包含 8 块：

```text
/goal [一句话目标，包含最终结果，不写空泛动词]。
验证：[具体命令 / 日志 / 截图 / 文件 / API / 清单 / 浏览器或本地运行证据；如果用户不知道，写「先发现并报告可用验证方式」]。
约束：[不能破坏的行为、接口、数据、风格、依赖、安全规则；写入新手/AI 常见错误]。
边界：[允许写入的位置、文件、模块、页面；禁止触碰的路径、系统、私密数据、破坏性操作]。
迭代策略：[每轮根据最强失败证据或未满足验收项选择下一步；优先最小可验证、可回滚动作；不做无关重构；连续无改善时停下报告]。
完成条件：[行家认可的验收标准 + 可复核证据 + 最终报告要求]。
暂停条件：[需要凭证、付费、生产数据、删改数据、改 schema/API、安装依赖、法律/医疗/金融判断、版权授权、范围扩大、验证冲突或所有权不清时暂停]。
进度：[按 checkpoint 汇报当前阶段、改了什么、验证结果、剩余问题和阻塞]。
预算：[N tokens / 时间上限]；达到预算仍未完成时，停止并报告已完成工作、失败尝试、剩余风险和下一最佳 checkpoint。
```

## 追问漏斗

### 前置原则：先翻译，不甩表

用户大概率只能说出「我想让 Codex 一直把这个做完」「帮我把这个项目修好」这种原始意图。不要问他「请提供 Objective、Scope、Done when、Stop if」。应该先把他的原话翻译成一版草案：

```text
我先按 Goal 来猜：
- 终局：____
- 完成证据：____
- 允许范围：____
- 必须停止：____

我不确定的是 2-3 个点：____
```

再追问最关键的缺口。原则是识别优先于描述，确认优先于构造。

用户可见追问要低术语：

- 不问「Scope 是什么」；问「哪些文件、页面、功能区可以动？哪些绝对别碰？」
- 不问「Verification command 是什么」；问「你知道平时怎么检查它有没有成功吗？不知道就让 Codex 先找」
- 不问「是否允许 schema migration」；问「要不要动数据库结构或已有数据？如果要动，必须先停下来问你」
- 不问「benchmark 指标」；问「有没有一个具体数字要变好，比如速度、分数、通过率？」
- 不问「Stop if 条件」；问「出现哪些情况你希望它别硬做，先回来问你？」

用户说「不知道」时，给保守默认值：

- 验证方式不知道：写「先发现并报告可用验证命令」
- 范围不知道：限制在当前任务直接相关文件，不做跨系统改动
- Stop if 不知道：默认权限、数据破坏、依赖安装、范围扩大、验证冲突都停
- 预算不知道：按任务大小给建议值，并写预算耗尽时的报告义务

第一轮优先问这 4 个：

1. 你想让 Codex 最后把什么做完？我先猜几个方向：
   A. 做出一个新功能、页面或工具
   B. 修一个一直报错、跑不通或时好时坏的问题
   C. 按已有计划/清单把一批事项做完
   D. 改一块旧东西，但尽量不影响原来的用法
   E. 让某个结果变好，比如速度、分数、通过率

2. 完成以后用什么证明？
   A. 它自己检查没有报错
   B. 项目能正常打开、启动或跑起来
   C. 页面截图/浏览器里看起来正常，主要操作也能用
   D. 计划或清单里的事项全部打勾
   E. 有一个具体数字达到目标，比如速度、分数、通过率
   F. 还不知道，让 Codex 先找怎么检查

3. 范围在哪里？
   A. 只动某几个文件/文件夹
   B. 只动某个页面/功能区
   C. 按已有计划、说明文档或问题记录执行
   D. 当前项目里都可以看，但不能乱动外部系统或私人数据
   E. 还没定

4. 哪些情况必须停？
   A. 要删除数据、改已有数据，或动数据库结构
   B. 要安装新东西
   C. 要动到一开始没说的地方
   D. 检查结果互相矛盾，不知道该信哪个
   E. 遇到账号、密码、权限、外部服务不可用

第二轮补齐：

- 开始前先看哪些资料？比如已有计划、说明文档、问题记录、截图、报错信息
- 哪些文件、页面、功能区绝对不能改？
- 只能使用哪些材料、工具、文件范围或账号范围？
- 每轮继续做时，Codex 应该按什么证据选下一步？如果用户不知道，就写「优先处理当前检查失败或还没达到完成标准的最小问题」
- 最多让它跑多久、尝试多少次，或花多少额度？
- 进度汇报要多细？比如每个阶段说清楚：现在做哪一步、改了哪里、检查结果、还剩什么、卡住点
- 这件事真正的行家是谁？他会用什么细节判断结果合格？
- 新手或 AI 最容易把这件事做错成什么样？这些错误要写进最终提示词的限制和停止条件里

## 强制反模糊

看到这些词，必须拦：

- 「全部」
- 「全面」
- 「优化一下」
- 「清理干净」
- 「做到最好」
- 「你自己决定」
- 「一直做到满意」
- 「尽可能」

替换方式：

| 弱表达 | 强表达 |
|--------|--------|
| 优化性能 | 让 checkout benchmark p95 < 120ms，并保持 correctness tests 通过 |
| 修所有问题 | 修复 `npm test` 当前失败的 7 个 case，不改测试断言来制造通过 |
| 重构代码 | 重构 auth 模块，保持 public API 不变，`npm test` 和 `npm run typecheck` 通过 |
| 做完 PLAN.md | 按 PLAN.md 的 checklist 逐项完成，每项提交文件证据和验证命令 |
| 页面看起来正常 | 用浏览器打开页面，保存截图，确认移动端和桌面端无重叠、无空白、主要交互可用 |

## 行家验收和失败预演

Goal 模式尤其容易出现「看似完成，实际行家不认」的问题。生成 `/goal` 前必须做一次内部失败预演：

1. 真正的行家是谁？
2. 他会看哪些细节判断这个结果能不能交付？
3. AI 最可能用什么方式假完成？
4. 如果这些错误出现，应该继续修、回滚，还是停下来问用户？

落地规则：

- `完成条件` 写行家验收标准，例如「移动端和桌面端截图都无重叠」而不是「页面完成」
- `边界` 写清能用什么输入、工具、文件范围和操作边界，避免 Codex 为了推进任务擅自越界
- `迭代策略` 写清每轮怎么选下一步，例如「优先修当前失败测试，不做无关重构」
- `约束` 写常见错误，例如「不要为了性能分数移除可见内容」
- `暂停条件` 写错误形态，例如「如果必须改后端 API 或牺牲核心体验才能达标，停止」

## 审计友好度评分

满分 10 分：

| 维度 | 分值 | 评分标准 |
|------|------|----------|
| 目标单一度 | 2 | 只有一个终局；没有混多个项目 |
| 完成证据 | 2 | 完成条件能映射成行家验收标准、测试、截图、文件、指标 |
| 范围约束 | 2 | 明确能改什么、不能改什么、只能使用什么输入/工具/操作边界，以及必须避开的常见错误 |
| 停止条件 | 2 | 遇到破坏性动作、权限、冲突、范围膨胀、专家会拒绝的错误形态会停 |
| 进度闭环 | 2 | 有 checkpoint、下一步判断规则、汇报格式、预算或上限 |

低于 7 分，不输出最终 `/goal`。先追问缺失项。

## 典型反例

不要输出：

```text
/goal 帮我全面优化这个项目，直到你觉得没问题。
```

原因：

- 目标不单一
- 没有范围
- 没有完成证据
- 没有停止条件
- 高概率空转、浪费额度后假完成

改成：

```text
/goal 将 React 应用的本地 Lighthouse 首屏加载时间降低至少 30%，同时保持现有测试通过。
验证：先读取项目脚本，找到构建、测试和 Lighthouse 或等价本地性能检查方式；修改前记录 baseline，修改后记录 final；运行现有测试命令。
约束：不改变后端 API、数据库结构、认证行为和可见产品内容；不为了分数移除核心内容；不安装新付费依赖。
边界：只修改前端源码、资源加载逻辑和直接相关构建配置；不触碰后端系统、生产数据、私密凭证或破坏性操作。
迭代策略：每轮根据最强缺口选择下一步，优先处理 baseline、final 或测试结果中最明确的问题；采用最小可回滚改动；连续两轮无改善时停下报告证据和阻塞。
完成条件：baseline 和 final 结果都被记录；final 首屏加载时间比 baseline 至少降低 30%；现有测试通过；最终报告列出修改文件、命令、前后数字和剩余风险。
暂停条件：需要改后端 API、数据库、认证流程、安装新依赖、移除可见内容，或 Lighthouse 本地无法运行且找不到可接受替代证据时暂停。
进度：按 checkpoint 汇报当前阶段、改动文件、验证结果、剩余问题和阻塞。
预算：120000 tokens；达到预算仍未完成时，停止并报告已完成工作、失败尝试、剩余风险和下一最佳 checkpoint。
```
