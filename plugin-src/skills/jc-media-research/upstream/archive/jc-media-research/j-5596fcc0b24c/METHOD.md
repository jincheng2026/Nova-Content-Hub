# jc-media-research

把「搜到一些热门内容」做成一条可复算的决策链：搜索、硬筛选、读取真实内容、整理评论、生成报告，再使用本人材料写稿。默认让用户说一句完整需求后直接拿到结果，不把内部计划、费用校验和中间选择变成聊天轮次。

## 先判断任务

把请求路由到最小任务，不默认执行全流程：

1. 方向或关键词：搜索、去重、筛选、给候选。
2. 单条视频：取得可靠字幕或本地转写，再按时间轴拆解。
3. 单个账号：整理账号、作品和评论，并读取各支柱头部作品的真实内容样本（字幕、逐字稿或本人档案），按三层定位（个人定位、账号定位、内容定位）拆解，寻找重复出现的模式，输出「值得借鉴／不建议直接模仿」两栏结论。
4. 个人口播：先读取用户的真实经历、观点和数字，再共同写稿。
5. 只有用户明确要求完整研究时，才依次执行以上路径。

开始前读取 [routes-and-gates.md](references/routes-and-gates.md)。遇到新的内容方向，先质疑需求，再删除无用步骤，随后简化、加速，最后才自动化；证据质量检查必须保留，但默认在后台完成。用户的判断发生在完整结果交付之后：采用、修改或放弃哪个选题，不靠流程中的「确认」「继续」和「选一个」来体现。

## 默认一次完成

用户已经给出明确任务时，直接完成当前任务并交付结果。搜索计划、实时价格、计划哈希、dry-run、任务级自动授权、请求、去重、筛选和报告生成都是后台步骤，不逐项展示，也不要求用户回复。

正常任务只允许以下三种原因追问，而且一次只问一个能解除阻塞的问题：

1. `required_input_missing`：缺少链接、平台、内容方向或不可替代的本人材料，现有信息无法完成任务。
2. `cost_limit_exceeded`：任务累计将超过 120 次付费请求或 1.00 美元，需要用户明确批准超出的新计划。
3. `execution_failed`：鉴权失败、媒体不可读、费用状态不明等真实失败，必须由用户采取动作后才能继续。

找到 3 条、1 条或 0 条合格样本都属于完整结果，不是失败。直接生成最终报告，说明真实数量和原因，不再问「要不要继续」「请选择样本」或要求确认已经算出的结果。

## 首次使用先检查

只在首次调用或运行状态不明时完成以下检查，不开始正式调研，也不发起网络或付费请求：

```bash
python3 scripts/validate_and_package.py validate
python3 scripts/tikhub_guard.py self-test
python3 scripts/tikhub_guard.py credential-status
python3 scripts/transcribe_segments.py --check
```

把结果分成三档告诉用户：

1. Skill 安装成功后，已有 CSV、JSON、报告、逐字稿和本人材料可以立即离线处理。
2. TikHub 凭据显示 `configured: true`，只表示凭据已保存；在首次实际任务的受限样本请求中验证 Key 和端点权限后，才能确认可以获取哪些真实平台作品、账号和评论。每批请求仍须经过后台费用门；任务累计不超过 120 次且 1.00 美元时不打断用户。
3. SenseVoice、FFmpeg、FFprobe、Node 和 sherpa 全部可用，只表示具备本地转写条件；真正开始转写前仍须确认媒体完整、可读。

缺什么就一次只带用户处理一项。不得让用户把 TikHub Key 发进聊天框，也不得打印凭据值。macOS 缺少凭据时，让用户打开「终端」并执行下面一行；`-w` 必须放在最后。终端出现密码输入提示时，让用户粘贴 TikHub Key，不是 Mac 登录密码：

```bash
security add-generic-password -a tikhub -s tikhub-api -U -w
```

执行后再次运行 `credential-status`，只报告是否已配置。非 macOS 环境继续支持 `TIKHUB_API_KEY`、`TIKHUB_TOKEN` 或 `TIKHUB_BEARER_TOKEN` 本机环境变量，但不把值写进聊天、报告、命令参数或 Skill 文件。

## 守住五条边界

1. 把用户放在真正需要判断的位置。AI 负责搜索、整理、计算、核对、选出当前任务内最值得看的样本和起草；用户在完整交付后决定采用、修改或放弃什么，以及确认自己的观点、经历和最终稿。
2. 把原始事实、程序计算、分析推断、用户确认和待验证分开。没有证据时直接写「待验证」。
3. 不用低质量内容凑数量，不跨平台混用指标，不把当前粉丝数冒充发布时粉丝数。
4. 不从标题或简介推断「前 5 秒」和视频结构。没有可靠字幕或逐字稿，就停止这部分结论。
5. 不编造用户经历、比例、时间、收入、效果或立场，也不把对标账号的数据改写成用户的第一人称成果。先查用户已指定的真实材料；缺失不影响主体交付时用 `[待补]` 留位并给可用结构，只有缺少不可替代的关键输入时才追问一次。

## 执行流程

### 1. 建立任务目录

在用户指定的项目目录创建独立任务目录，至少分开：

```text
raw/          原始响应，仅本地保存
normalized/   白名单字段和逐行标签
transcript/   原始识别、分段复核、校正版
reports/      报告、图表、明细和证据索引
feedback/     本次接受、拒绝、修改和原因
```

不要把真实任务数据写入 Skill 目录。已有目录或文件默认不覆盖。

### 2. 设计搜索

读取 [search-and-selection.md](references/search-and-selection.md)，记录平台、关键词组、排序方式、时间范围、分页、请求上限和停止条件。

抖音 AI 教程默认先执行硬门槛：粉丝数 100–20,000、点赞数不少于 1,000、与方向直接相关。最近 90 天是优先条件，不是降低其他门槛的理由。合格样本不足时扩关键词、排序和时间范围；仍不足就返回真实数量。

已有 CSV、JSON 或报告能够回答问题时，先离线处理，不重复付费采集。

### 3. 过费用门

任何付费请求前：

1. 先从实时 OpenAPI 确认端点和价格。
2. 生成计划，列出端点、请求数、预计最高费用、样本范围和停止条件。
3. 同一任务默认累计允许 120 次请求，预计费用累计不超过 1.00 美元。够把一个账号的作品翻完、多条视频的评论抓够，不要为了省几分钱交半截结果。
4. 在默认上限内，由守卫脚本生成与计划哈希绑定的任务级自动授权并直接执行，不要求用户手动回复 `APPROVE`。
5. 超过默认请求数或费用上限时，只问一次并展示超出部分、完整计划哈希和最高费用；必须取得匹配的明确批准才能继续。
6. 费用状态不明、鉴权失败或超时后是否扣费不明时停止，不盲目重试；未知扣费仍占用任务预算。

使用 `scripts/tikhub_guard.py` 执行受保护请求。不得绕过脚本直接循环调用付费接口。

默认上限内，生成计划后在同一任务目录执行：

```bash
python3 scripts/tikhub_guard.py auto-approve \
  --plan TASK/raw/plan.json \
  --budget-ledger TASK/raw/task-budget.jsonl \
  --out TASK/raw/approval.json
```

随后用同一 `approval.json` 执行与该计划哈希完全一致的请求。预算账本是任务级累计账本，不能每批新建来重置上限。

使用自动授权执行时，`run` 必须同时传入同一个 `--budget-ledger TASK/raw/task-budget.jsonl`；守卫会再次核对授权中的 reservation hash、计划哈希和累计上限。显式超限批准不需要这个参数。

### 4. 规范化和筛选

使用 `scripts/prepare_research.py` 生成白名单数据、稳定来源链接、去重结果、合格列表和逐条排除理由。完整字段和分类规则见 [data-contract.md](references/data-contract.md)。

硬门槛先于排序。只在合格样本内部按透明指标排序，不使用无法解释的综合分。把少于 100 粉、超过 20,000 粉和少于 1,000 赞的内容放进各自参考区，不标为已验证低粉爆款。

### 5. 读取真实内容

优先使用可靠官方字幕或作者提供的逐字材料。没有可靠字幕时，使用本地 SenseVoice Small：

```bash
python3 scripts/transcribe_segments.py --input MEDIA --output-dir TASK/transcript
```

脚本按约 28 秒串行切片，保留原始识别、分段复核、待校正层和 manifest。只纠正确定错误，保留口语表达；不确定处明确标记。缺少 SenseVoice、FFmpeg、媒体不可读或转写不完整时停止，不自动换成云端模型。

读取 [evidence-analysis.md](references/evidence-analysis.md) 后再分析视频、账号和评论。至少两条独立视频出现同一模式，才能写成重复规律；一条只能写成单次观察。

凡是要写前 5 秒、时间轴、钩子、转折或内容结构，先运行：

```bash
python3 scripts/validate_transcript_ready.py --transcript-dir TASK/transcript
```

返回 `ready` 才能继续。返回 `blocked` 时先完成逐字稿复核，不能拿标题、简介、原始识别或占位校正版代替，也不能在报告中写精确时间点和结构结论。

### 6. 完成当前任务

关键词或方向任务直接交付全部合格样本、证据、排除原因、限制和可视化报告，不要求用户再选一次。用户明确要求完整研究时，在费用、材料和证据允许的范围内，按最近 90 天优先、相关性和透明互动指标自动选择最多 3 条继续深挖，并在报告里写明选择依据。不要无边界下载或抓完整评论区。

交付完成后可以列出可选的后续动作，但不能把它们写成当前结果的阻塞问题，也不能用问句逼用户继续。

### 7. 生成报告和图表

按 [reporting-and-security.md](references/reporting-and-security.md) 和 [report-template.md](assets/report-template.md) 写报告。内容搜索、账号研究、视频拆解和评论研究的主报告都必须是自包含 HTML；Markdown 只能作为证据伴随文件，不能作为唯一报告。所有数据图表统一走 `assets/page-template.html`（内联 ECharts，页内有已验证的图表模式和使用说明）+ `scripts/qa_page.py` 渲染自查，机械检查 PASS 且分区截图逐屏目检通过才交付；禁止徒手计算 SVG/HTML 坐标画数据图。`scripts/render_report.py` 为旧版手写 SVG 渲染器（legacy），仅在模板路径不可用时兜底；报告要有首屏结论、与当前任务相符的数据卡、研究范围和限制。内容搜索和筛选报告还要有合格样本、排除原因，并在正文直接嵌入真实数据驱动的筛选漏斗、粉丝数—点赞数散点图、粉丝体量分层梯形图和排除原因条形图；账号、视频和评论报告使用 reporting-and-security.md「不同任务的最小图表」所列对应图表，不为补齐搜索图位追加本次无关的采集或筛选。不能只用数字卡片、进度条或 Markdown 长表冒充可视化。图表的数据不足时保留对应图位并直说缺少哪些字段，不补点、不推算、不隐藏 0 结果。需要独立图表证据时，再使用 `scripts/render_charts.py` 生成 SVG、明细 CSV 和 manifest。

每份 HTML 主报告生成后，必须立即生成同名 PNG 预览并验证：

```bash
python3 scripts/render_report_preview.py \
  --input TASK/reports/research_report.html \
  --output TASK/reports/research_report_preview.png
```

最终回复先直接展示 PNG 预览，再给 HTML 主报告和证据文件路径；不能只回一句「报告已生成」或只给本地 HTML 路径。预览失败不等于研究失败，但必须明确说明「HTML 内有图，当前无法生成聊天预览」，并提供一个能解决的动作。

每一个重要结论都附证据 ID、来源链接或本地源文件；每个比例写清行数、噪声处理和分母。

### 8. 使用本人材料写稿

读取 [writing-and-feedback.md](references/writing-and-feedback.md)。先在用户指定的项目、知识库或 `--profile-path` 中找真实资料，不把本机固定路径写进 Skill。材料足够时直接交付完整稿；部分材料缺失但仍能诚实写作时，交付完整结构或草稿并用 `[待补]` 标明缺口。只有缺少不可替代的核心观点或经历、导致继续必然编造时，才按 `required_input_missing` 问一个问题。

写稿前在后台生成一张不发给用户确认的写作卡：目标观众、唯一主要收获、可信证据、用户本人的判断、可用画面、不能说的内容。它只是内部检查，不增加聊天轮次。口播遵循「真实需求 → 新可能 → 简单做法 → 可见结果／可信证据 → 用户判断」；不是把研究报告压缩成口语，也不是按选题、评论、结构、写稿机械报菜名。

用户说「结合刚才找到的选题、评论需求和爆款结构」时，直接复用本次对话已经取得的材料，不要求重新粘贴、重新选题或再次确认。若用户在同一条消息或既有本人材料中已经给出一个真实经历／操作，以及一个明确观点，就视为写稿输入完整：自动选取当前最值得拍的选题和最集中的评论需求，直接交付完整口播，不先发提纲，不询问时长、平台、风格或是否继续。用户明确给出时长等要求则照做；未给出时按适合当前内容的短视频长度起草，并标明实际字数，不虚构精确时长。

交付前静默检查并自行修改一遍：观众能得到什么、开头是否让人停下、每句话是否像人会说的话、事实是否有证据、每段是否有能展示的画面、是否每段都增加了新信息。正文先给干净口播，再给极短的「画面落点」和「材料对应」。未指定平台或转化目标时不补通用「点赞收藏关注」；结尾优先落在用户真实判断上。

用户确认某段文字后固定原文，不继续发散。记录本次接受、拒绝、修改、原因和最终稿；一次修改只算单次观察。至少两个独立任务出现相同理由后，才能建议形成长期偏好，且必须再次请用户确认。

### 9. 验证和公开分享

公开分享前运行：

```bash
python3 scripts/validate_and_package.py validate
python3 scripts/validate_and_package.py package --out jc-media-research-public.zip
```

扫描命中密钥、令牌、Cookie、签名 URL、个人账号字段、真实任务数据或本机绝对路径时必须失败。公开包不包含模型、依赖目录、缓存、真实评论、原始 API 响应或用户资料。

## 完成标准

按本次选定任务检查以下条件，只在适用项全部满足时说该任务完成。评论标签、视频逐字稿、本人材料、图表和口播检查分别在本次涉及对应内容时适用；不为勾齐未涉及的项目自动追加采集、评论分析、转写或写稿。完整研究仍检查全部实际涉及的步骤，缺失必要证据的部分不得以「不适用」跳过。

- 范围、时间和样本数写清楚。
- 每条 normalized 数据可回到来源。
- 筛选和排除原因可复算。
- 评论比例来自逐行标签。
- 视频结构有字幕或逐字稿支持。
- 精确时间轴和结构分析前，逐字稿验证脚本返回 `ready`。
- 用户经历和数字有本人材料支持。
- 内容搜索和筛选的 HTML 主报告含筛选漏斗、粉丝数—点赞数散点图、粉丝体量分层梯形图和排除原因条形图；账号、视频和评论报告满足各自图表要求。图中数量、点、分层和条都能回到对应证据明细或 summary；对应图表字段不足时明确降级而不造数据。
- 原始数据与公开交付分开。
- 费用没有超过任务级自动授权或用户明确批准的范围。
- 普通成功路径没有要求用户追加确认，3 条或 0 条结果都已直接交付。
- 内容筛选任务已生成并验证 `reports/research_report.html`。
- 内容搜索、账号、视频和评论主报告均为自包含 HTML，并生成可直接展示的 PNG 预览；最终回复已先展示预览再给 HTML。
- 口播已经通过收益、口语、事实、画面和信息密度五项静默检查，没有把对标数据写成用户的第一人称经历。
- 需要用户本人判断的内容在交付后清楚标明，最终稿状态清楚。
