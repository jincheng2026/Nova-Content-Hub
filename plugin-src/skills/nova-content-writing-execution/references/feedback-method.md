# 反馈、改稿证据与知识候选

## 何时记录

用户具体评价、否决、纠错、手改、确认，或真实试读/录制/发布结果改变了判断时记录，不等锁稿。纯提问、发散讨论、未采纳的 AI 建议和已完整记录的重复表态不制造新反馈。用户要求只讨论、不保存时优先遵从。

从当前内容和相关任务中回读已有 feedback/knowledge，按同一事件与证据去重；已提交成功的反馈不另写一份。用户直接在创作页修改而没有解释时，记录客观差异，原因写为未知或明确的 AI 归纳，不让用户重新填表。

## 一条可复用反馈的内容

在 feedback artifact.text 中完整写明下列信息，结构化附件仅作补充，避免关键理由只存入下游不会展示的 data：

| 内容 | 如何写 |
| --- | --- |
| 关联与阶段 | 当前 contentId/T 编号、任务/产物引用；找参考、叙事、写稿、画面、包装等 |
| 原始事件 | 用户实际原话或准确转述；来源是聊天、批注、亲手修改还是实际结果 |
| 具体改动 | 原句→新句、谁改、发生在哪一轮；整段重写给整段概述 |
| 原因性质 | 用户明确说的原因、用户确认过的理解、AI 归纳或未知，分开写 |
| 采用与结果 | 对话确认、已保存、实际发布或外部状态未知；效果待观察/有证据有效/有证据无效 |
| 证据与边界 | 可回到哪个原稿/批注/结果、仅适用何种场景、还缺什么 |

示例的组织方式：用户把“输入全部资料”改为“先选需要分析的文件”；客观变更如实记录。若用户未说原因，可以提出“可能为了限定范围”的 AI 归纳，但不能把它写成“用户要求所有教程都限制文件数量”。

新反馈推翻旧解释时追加校正，引用旧记录，不删改历史使其看似从未发生。对话没有确认不等于现实没采用；实际发布证据存在时以真实版本为准。

## 从案例到判断

先对照已有已采纳知识的原文、适用条件和证据。按本轮实际内容提出一种处理：

- 补充证据：相同判断和边界得到新案例支持。
- 收窄边界：出现反例或明确前提，说明原判断在哪些条件下不适用。
- 保留案例：只有一次选择、原因不明或具有明显内容特性。
- 暂不沉淀：信息不足、重复或不影响后续决定。
- 新的判断候选：有可解释的跨内容价值，列正例、反例/未验证处和适用场景。

至少两条独立内容出现相似取舍才称重复证据；重复本身不自动证明规则成立。用户明确表达的个人偏好可以作为偏好候选，不能称已验证的市场规律。对标作者的方法标市场观察，用户表达偏好标个人判断，工具/流程问题标改进建议。

## 人工决定与下一条读取

需要长期采用时提交 knowledge 候选，text 包含建议判断、来源记录、适用范围、理由和不确定性。存在近似旧规则时把旧文与建议并排说明是补证据还是改边界；当前接口只能新增候选时不冒称已合并更新旧规则。

采纳由工作台人工决定；不自动修改 SKILL.md、已采纳规则或私人知识库。技能步骤问题也先提可追溯改进建议，只有另获明确修改任务才处理文件。

下一条创作从 context 读取已采纳知识，选择与本条阶段/类型/条件相关的项，在工作依据中注明引用；未采纳候选可以供讨论，不能当已确认偏好。当前事实与旧规则冲突时保留证据，只有冲突会改变当前交付且无法自行核实时才请用户裁决。

## 验证学习是否发生

用后续真实内容观察是否再次犯同类问题、初版结构保留情况、用户重写位置、实际试读/拍摄帮助和可核实耗时。没有基线不报固定效率提升；一条内容成功不等于方法成熟。

完成条件：本轮真实反馈有可回读产物，每个长期候选有证据和边界，人工采纳状态没有伪造。交付说明本次记录了什么、哪些只是案例、哪些待决定；不把知识列表变长当作学习质量证明。
