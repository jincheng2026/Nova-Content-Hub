Hello，各位，最近我一直在用 Claude Code。它是一个跑在终端里的 AI 编程助手，没有 GUI，没有弹窗，就是一个黑色的命令行窗口。这个叫什么呢？这个叫 CLI。

那我的第一反应就是，Anthropic 这么大的公司，为什么做出来的东西是在 CLI 里面，一个黑色的框，这么简陋？但用了一段时间以后，我改变了自己的想法。CLI 不是一个妥协，反而是经过深思熟虑的架构决策。

理解这个决策，我觉得能够帮你看清 AI Agent 时代软件设计的底层逻辑。

我先从一个根本的问题出发，AI 到底是怎么去看软件的？那我们知道，人是有视觉的，按钮我能看出来是红色的，菜单我可能看出来是在左边的，你扫一眼就知道该点哪里。这个是几十年 GUI 设计的前提假设。

所以 GUI 就是图形化界面，它的假设就是用户有眼睛。但是 AI 没有眼睛，它的感知通道是什么呢？是 Token 序列，是文字，是结构化的符号流。

所以如果你让 AI 操作一个 GUI 程序，中间会有多少层转换呢？我给大家列一下。比如说我先有一个软件界面，我可能会把它截出来，这有个按钮，这有个菜单。然后我通过视觉模型识别界面元素，比如按钮在这里，菜单在那里。然后我模拟鼠标做一次点击，点击完以后，我等待这个 UI 给我响应。响应完以后得到一个新的界面，然后我再截图确认。

每一层都是误差的来源，每一层都在浪费推理资源，处理 AI 本来根本就不需要面对的视觉噪声。

那命令行是另一套逻辑，输入的是文字，输出的也是文字，这个是 AI 能够理解的 Token，转换零摩擦。

所以 Claude Code 选择 CLI，第一个原因我觉得就在这里：把 AI 放在它最擅长的感知环境里面，而不是强迫它适配一个为人类视觉系统设计的界面。

好，那就来讲第二个，叫作为什么命令行自带说明书。这件事比你想象的会更加重要，这个我觉得是最被低估的一个点。

AI 要学会一个工具，首先得知道这个工具的说明书。传统方式就是工程师写一个文档，AI 读文档，然后 AI 调工具。这中间有个断层，就是文档是静态的，工具是动态的，两者随时可能对应不上。

那命令行工具有一个几十年形成的规范。大家想一下，是什么呢？是这个命令 `--help`。我相信大家现在用命令行经常会用这个命令。你运行 `claude --help`，就能够立刻得到完整的能力清单、参数说明、用法示例。

这个是工具运行时候的自描述。工具被调用的那一刻，直接告诉调用方，我自己能做什么。那如果工具更新一下，`--help` 这个命令里面的内容也会随之更新。OK，这样就保证了时效性。

那对 AI 来说，这意味着什么呢？它意味着 AI 不需要依赖训练数据里的知识去判断工具的用法，因为那些知识可能是过时的。它可以在运行的时候动态查询，拿到最准确的信息，再决定怎么调用。这个就是一种自适应的工具发现机制。

但是 GUI 图形化界面是没有这样对应的东西的。所以 Claude Code 深度利用了这个特性。它能够读取项目里的工具配置，能够理解构建脚本，能够调用系统上已经有的各种 CLI 工具。因为这些工具天然就是可以被程序调用、可以自描述的。

那 Claude Code 的 CLI 和这种普通命令行到底有什么本质的区别？我觉得区别在于，到底是为谁设计的。

传统 CLI 的用户是程序员，错误信息简单粗暴，因为程序员看一眼就懂了。输出格式可以只有纯文本，因为程序员会用大家熟知的像 `grep` 命令、`awk` 命令，做检索和筛选。

那 Claude Code 这类新一代工具，用户是 AI Agent。所以这就带来几个关键设计的差异。

首先，结构化输出是最高优先级的。不是顺便支持 JSON，而是默认输出就应该是可以被程序解析的格式。它就一定得是 JSON，或者各种比较结构化的格式，不需要再做文本解析这样的复杂工作。

第二个，错误信息要可操作。传统工具报错了，会说 Permission Denied，那 AI 看了只能停下来。但是好的 AI Native 工具会说，读取这个目录可能需要一个 `sudo` 权限，或者你可以用 `chmod` 修改这个目录或者文件，再去重试。这样，错误信息本身就包含了下一步的行动路径，AI 可以自主决策是不是继续执行。

OK，第三个，就是操作要可预览、可回滚。因为 AI 会犯错，它可能会误解你的意图。Claude Code 在执行危险操作前会展示计划，我们定义为 Plan。你看，它会说，可能会修改这三个文件，删除两个函数，理由是什么。然后你确认，再执行。

这个不是多余的步骤，这个叫作人机协作的信任建立机制。

OK，那接下来再聊一聊，CLI 在 AI Agent 的架构里面到底扮演什么角色。我在这里想给大家分享一个很多文章都没有讲清楚的事情，就是 CLI、MCP 和 Skill 到底是什么关系，为什么 Claude Code 把它们都用上了。

OK，那首先，CLI 是工具本身，像扳手、像螺丝刀，是能够实际干活的东西。Claude Code 本身是一个 CLI，它也能调用系统上其他的 CLI 工具。

MCP，模型上下文协议，是工具的接入层，把工具提前注册到 AI 的上下文里面。你可以理解为它是一个 Interface，让 AI 知道我现在手边有哪些工具可以用。这个是常驻的工具清单，会占用上下文窗口，但换来的是随时可调用。

那 Skill 是一个手册，我们定义为 Manual，工具手册。它告诉 AI 在什么情况下用什么工具、怎么用最高效、遇到哪些情况要特别注意。所以没有 Skill，AI 也能用工具，但得靠自己摸索；有了 Skill，成功率能显著提升。

OK，那 Claude Code 最聪明的地方，在于它把这三层整合在一个体验里面。你装上 Claude Code，它既是工具，又通过 MCP 把自己注册成了可调用的能力，同时还内置一套编程场景的最佳实践。所以你拿到的不是一个孤零零的工具，AI 又多了一个完整的技能，而不是单独的三块需要自己拼装。

那我觉得，这是整件事情最值得想的地方。过去四十年，计算机接口的进化方向是降低人类的学习成本。比如说，从命令行到图形界面，然后可能再到触摸，对吧？越来越直觉，越来越傻瓜。

这背后的假设，是用户是普通人，时间很宝贵，认知资源是有限的。但是现在这个假设正在松动。

不是说图形化界面会消失，因为图形化界面 GUI 对人类用户来说还是友好的。但软件的调用链正在变化。以前人类直接调用 GUI，但是现在中间加一层 AI，人先调用 AI，AI 再调用这个软件。

所以在这个两层架构里面，AI 是软件的直接用户，人类退到了意图表达层。比如你说，“帮我把这个功能重构一下”，这很模糊，是抽取成独立函数呢，还是改成异步呢，还是拆出模块呢？但是 AI 负责把这个模糊的意图翻译成精准的操作序列，再通过 CLI 执行。

所以这种分工，我觉得非常优雅。自然语言的模糊性交给 AI 处理，精确执行交给命令行。人类不需要学命令行，AI 也不需要假装是有眼睛的。

所以回到原始概念，CLI 的回归不是为了纯粹复古，而是这个接口设计真的在适应新的直接用户。所以 CLI 的这波复兴，本质上就是软件在重新校准它自己服务的对象。

我们都知道 Claude Code 现在已经相当好用了，但我还是想分享一下，我自己使用过程中注意到的几个还没有解决的问题。

第一，工具发现没有基础设施。你怎么知道有什么好用的 CLI 可以让 Claude Code 调用呢？现在基本靠社区的口口相传，没有一个结构化的目录。这就相当于 NPM 出现之前的 JavaScript 生态，工具存在，但是发现成本很高。

第二个，权限的粒度还很粗。我接入一个工具，基本上就是全权限的。那我还是希望能够告诉 Claude Code，你可以读这个项目代码，但是不能执行 `git push`，然后这个约束在工具层面上就生效，而不是靠我的人工确认每一步。

第三个，就是跨工具的认证没有统一。Claude Code 调用不同的外部服务，每个服务都有自己的 Token 管理方式。这个碎片化会随着 Agent 能力的拓展越来越明显。

所以谁来解决这三个问题：工具目录、细粒度的权限、统一身份认证？那我觉得，谁就在搭这个 AI Agent 时代真正的基础设施。

OK，所以 Claude Code 选择 CLI，不是因为 Anthropic 懒得做 GUI，而是因为当 AI 成为软件真正的用户的时候，三十年前为机器设计的这些接口，反而比三十年来为人类优化的接口更加合适。

这个是一个很反直觉的结论，但逻辑是清晰的：接口是为用户设计的，那用户变了，接口当然也得跟着变。

命令行等了四十年，终于等到了它最合适的用户，就是 AI。
