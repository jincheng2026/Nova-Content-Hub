# 输出合同

## 普通输出：BROK

用户确认镜像复述后，输出可复制到新聊天的提示词。

```text
### 可复制到新聊天的提示词

Background:
[身份、场景、动机。不要让用户重新说一遍。]

Missing Inputs:
[仅在信息不足但仍要输出提示词时使用。列出还缺哪些信息，以及会影响什么判断。]

Assumptions:
[仅在信息不足但仍要输出提示词时使用。写明暂时按什么保守默认处理。]

Role:
[具体行家角色。写专业能力、工作场景、判断手感，不写空泛专家。]

Objective:
[清晰、具体、可衡量、有边界的目标。]

Key Result:
[用户可以判断好坏的具体标准。]

Pitfalls / Avoid:
[复杂任务才加。写具体错误形态，不写「避免低质量」。]

Before Output:
[仅在缺失信息会影响定位、策略、成交路径、案例可信度或安全边界时使用。要求执行 AI 先追问最多 3 个问题，不要编造经历、案例、客户反馈或产品承诺。]
```

## Background 写法

必须包含：

- 用户是谁。
- 在什么具体场景。
- 为什么需要这个结果。

差：我是一个讲师。  
好：我是社区园艺公益课的志愿者，周末要带 20 名新手种植香草，现在要准备一份现场操作卡。

## Missing Inputs / Assumptions 写法

不是所有提示词都要加这两项。只有高依赖背景信息的任务缺材料时才加。

必须加的情况：

- 定位、个人 IP、品牌策略
- 商业方案、产品包装、销售转化
- 内容系统、课程设计、复杂决策
- 需要调用用户经历、案例、客户反馈、素材库或风格资产的任务

写法要求：

- `Missing Inputs` 写清还缺什么，以及缺口会影响什么判断。
- `Assumptions` 只能写保守默认，不要替用户编经历、案例、客户反馈或产品承诺。
- 如果缺口会改变最终方案方向，加 `Before Output`，要求执行 AI 先补问最多 3 个问题。

## Role 写法

不要写「专家」「顾问」这种空角色。

Role 要包含：

- 现实中哪类人最会做这件事。
- 他靠什么判断结果好坏。
- 他会避开什么新手错误。

差：你是一个运营专家。  
好：你是长期带新手做户外种植的志愿者，擅长把操作拆成低风险步骤；判断标准是新手能否在现场独立完成。

## Objective 写法

必须具体、可衡量、有边界。

差：帮我做个好方案。  
好：帮我设计一个 7 天 AI 学习打卡活动方案，包含每日任务、提交方式、激励机制和运营 SOP；不需要视觉物料。

## Key Result 写法

Key Result 是验收标准，不是愿望。

差：要有创意。  
好：每日任务要从简单到复杂递进；每个任务都能在 20 分钟内完成；提交物能证明学员真的做过，而不是只截图打卡。

## 一句表达建议

默认只给一句，不输出完整评分表。

```text
下次可以直接这样说：「____」。这句话补上了 ____，能减少来回澄清。
```

## 问题版本

当用户问「这个问题该怎么问」时，不强制 BROK。

```text
你可以这样问：

「____」

还可以补充这几个信息，让回答更准：
1. ____
2. ____
3. ____
```

## 决策提示词

```text
### 可复制到新聊天的决策分析提示词

Background:
[当前处境和为什么要决策]

Decision:
[要在什么选项之间做选择]

Criteria:
[判断维度：收益、成本、风险、时间、不可逆性、机会成本等]

Constraints:
[资源、时间、偏好、不能接受的后果]

Output:
请先列出关键判断，再给出推荐选择、理由、反方风险和一个最小验证动作。
```

## Skill 修改提示词

```text
### 给执行 AI 的 Skill 修改提示词

你要修改的 Skill:
[名称和路径]

当前问题:
[哪里不好用，来自用户反馈或样例]

保留:
[哪些能力、语气、边界不能丢]

修改目标:
[具体要改成什么]

边界:
[只评估 / 给改法 / 直接改真源 / 打包分享]

验收:
[如何确认改好了：主入口变瘦、路由更准、输出更稳、示例通过等]

停止条件:
[真源不清、权限不清、需要批量移动、会破坏兼容时停下来问用户]
```

## 评分输出

只有用户明确要求评分、复盘表达、教学提问时输出完整评分。

评分标准见 [scoring.md](scoring.md)。默认不要使用 emoji 或星星符号。
