## 公理

1. 前台极简，后台完整。用户每天只看执行必需字段；AI 可以在后台保留追溯、复盘、自动化需要的字段。
   - 违反的样子：主视图堆满重要度、风险、资料链接、复盘、原文证据，导致每天不想打开。
2. 先确认，再入库。AI 提取的任务只是候选，不是事实。
   - 违反的样子：从长文里猜出 20 条任务，直接写入飞书，后面还要人工清垃圾。
3. 每条任务必须能回到原文。没有证据的内容只能标为 AI 推断或待确认。
   - 违反的样子：原文只说「知识库还要推进」，AI 写成「今晚 9 点前发布知识库教程」。
4. 字段必须有存在理由。一个字段如果不帮助执行、查证、复盘、归因或后续自动化，就隐藏、合并或删除。
   - 违反的样子：为了看起来像项目管理系统，增加没人填、没人查的幽灵字段。
5. 写入飞书是工程操作，不是文本输出。用户只确认一次；确认后 AI 必须自动读取真实表结构，再映射字段、去重、dry-run、写入并回读验证。
   - 违反的样子：按脑内字段名直接调用 API，结果字段不存在、重复创建、写错表。

## 强制闸门

这些闸门必须显式执行，但全流程最多只有一次人工确认。

### CHECKPOINT 1：唯一一次用户确认

从口喷、长文本、聊天记录、会议纪要、文档中提取任务后，只能输出候选任务清单。

STOP：用户未确认前，禁止输出最终入库表，禁止写飞书。

用户确认候选任务后，该次确认同时授权真实写入。用户最初就明确说「加入计划」「记录到飞书」「写入飞书」，且任务无歧义时，该指令本身算唯一一次确认。

### CHECKPOINT 2：技术写入闸门

确认后生成最小入库清单，并自动执行真实 schema 读取、字段映射、去重和 dry-run。这些步骤用于防止写错，不得再询问用户「是否写入」。

STOP：没有真实 Base schema、字段映射、去重和 dry-run 时，禁止调用写入工具；技术检查通过后立即写入并回读验证。

## 触发后先分流

先判断用户这次要做哪一类事：

| 用户意图 | 处理 |
| --- | --- |
| 口喷今天/明天/本周计划 | 走「快速计划沉淀」 |
| 给一大段聊天、会议、文档、课程想法 | 走「长文本任务提取」 |
| 要把已确认任务放进飞书 | 走「飞书写入协议」 |
| 讨论 Base 字段、视图、表结构 | 走「字段必要性审计」 |
| 问今天做什么、分诊、排优先级 | 交给日规划类 Skill 或普通对话，不要抢路由 |

如果输入里既有背景又有任务，先分成两块：

- 背景：进入 `来源摘要` 或 `上下文`
- 任务：进入候选任务清单
