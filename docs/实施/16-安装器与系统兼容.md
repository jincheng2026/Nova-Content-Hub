# 安装器与系统兼容

本轮提供受限测试安装器的原生构建入口：Mac Intel `x64` 与 Apple Silicon `arm64` 分别生成 DMG；Windows `x64` 生成 NSIS EXE，Windows `arm64` 保留独立原生构建入口。每个目标必须在匹配的系统和架构上安装依赖、构建、验收，不能把 Apple Silicon stage 改名当成 Intel 包。

当前 `release.config.json` 仍是 prototype，桌面 release 强制 `experimental: true`、`productionReady: false`。认证尚未接入，安装器只接受 `AUTH_MODE=required`；新业务写入和 AI 交接被阻止，已有库读取及已有候选导出仍允许。文件名与应用名称带 `testing` / `Testing`，不是商用发行承诺。

## 构建命令

固定 `electron-builder@26.15.3`、`electron@44.9.0`，由 lockfile 管理。不要用会隐式下载最新版的 `npx electron-builder`。

在各目标的原生 runner 中，进入 `workbench/`：

```sh
npm ci --include=optional --no-audit --no-fund
npm test

# Apple Silicon macOS / 原生 arm64 Node
npm run dist:testing -- --platform darwin --arch arm64

# Intel macOS / 原生 x64 Node
npm run dist:testing -- --platform darwin --arch x64

# Windows x64 / 原生 x64 Node
npm run dist:testing -- --platform win32 --arch x64

# Windows ARM64 / 原生 arm64 Node；单独验收，不能复用 x64 的结论
npm run dist:testing -- --platform win32 --arch arm64
```

只执行与当前机器匹配的那一条。`process.platform` / `process.arch` 不匹配、未知参数、缺失参数、auth-disabled 均立即拒绝。入口先验证 root release 配置、工作台版本和已安装工具版本，然后调用现有 `build --auth required`，再核对 stage 的 platform、arch、version、pairId 和完整配置对应关系，最后运行本地 builder CLI，显式传 `--publish never`。

输出按目标隔离：

```text
workbench/release/darwin-arm64/testing/
workbench/release/darwin-x64/testing/
workbench/release/win32-x64/testing/
workbench/release/win32-arm64/testing/
```

文件名示例：`Nova-Content-Hub-0.2.0-darwin-arm64-testing.dmg`、`Nova-Content-Hub-0.2.0-win32-x64-testing.exe`。builder 配置一并留在对应输出目录供审查。

## 包内容与数据保留

桌面 worker 使用 Electron `utilityProcess`，不另嵌 standalone Node。独立插件继续由自己的构建脚本生成匹配架构产物；插件固定 Node 的 `nodeSha256` 会受重签影响，因此不把完整插件/固定 Node 塞进 `.app`。

安装器只包含桌面编译结果、所需文件业务库/bridge、资源、schema/reference 和生产依赖。分发脚本、测试、probe 入口、源码映射、独立插件 runtime 和锁文件不进入应用。`workbench/dist/release.json` 是运行时校验必需的 release 清单，应保留。

暂用 `asar: false`：现有文件工具依赖真实路径，sharp 原生库也保持已验证的目录结构，避免增加 ASAR 解包边界。若以后改为 ASAR，必须明确解包 `sharp/**` 与 `@img/**`，并重新验证 utility process、动态文件访问、图库与图片真实解码。ASAR 不是源码保密方案。

sharp 依赖本机平台的 optional 包，禁止 `--omit=optional`；现有 build 在 stage 中运行 `npm ci --omit=dev` 并做真实图片创建/解码校验。builder 不再次重编译或替换这些 N-API 库。还需在安装后的真实 Electron utility process 中验收；仅 Node 解码通过不足以代表安装包可用。

Windows NSIS 使用每用户安装、`asInvoker`、不允许提权、不打包 elevation helper，创建桌面/开始菜单快捷方式。`deleteAppDataOnUninstall: false` 保留 userData；用户自选文件库位于安装目录外，卸载不应删除。macOS DMG 只交付 `.app`，构建脚本不会复制到 `/Applications`，也不删除 userData 或文件库。升级和卸载的数据保留仍需各系统实机验收。

## 签名与正式发布门禁

测试包：macOS 使用 ad-hoc 签名，关闭 hardened runtime 和自动公证；Windows 允许未签名测试包。builder 子进程删除 `CSC_*` / `WIN_CSC_*` 签名变量，再显式禁用签名身份自动发现，避免误用开发机已有签名身份。不能把 `CSC_LINK` 设为空字符串：builder 26.15.3 仍会把它作为证书路径，解析到当前工作目录并报 `not a file`。这一分支有子进程回归测试，直接核对 builder 的证书选择结果为空。脚本不读取私钥，不移除 quarantine，不关闭 Gatekeeper，不修改系统配置。测试包可能被系统拦截；这不等于正式发行问题已经解决。

`npm run dist:production -- --platform <本机平台> --arch <本机架构>` 目前必须失败。它先检查签名配置是否存在（Mac 还要求公证配置），即使已配置也会因实验状态和认证未接入而拒绝；改 `productionReady` 或切 auth-disabled 不能绕过。正式签名、公证、Windows 签名验证和生产能力门禁需要专门实现、审查和实机验收，当前不会创建生产安装器。

未来生产产物应位于 `workbench/release/<platform>-<arch>/production/`，并采用独立生产身份；当前没有可运行的 production 打包路径。没有自动更新、云发布或自动上传。

## 系统底线与验收边界

| 目标 | 依赖给出的底线/产物目标 | 本项目安装包验收 |
| --- | --- | --- |
| macOS Apple Silicon arm64 | Electron 44 要求 macOS 13+；Info.plist 设置 13.0 | 本机 DMG 构建、产物架构与 ad-hoc 签名校验通过；挂载/安装后启动仍待实测，不承诺所有 macOS 13 机器可用 |
| macOS Intel x64 | Electron 44 要求 macOS 13+ | 未在 Intel 硬件验收 |
| Windows x64 | Electron 官方列 Windows 10+ x64 | 未在 Windows 硬件验收 |
| Windows arm64 | Electron/sharp 提供 ARM64 包 | 独立候选管线，未构建/验收，不与 x64 合并结论 |

当前 Electron 二进制的 `Info.plist` 为 `LSMinimumSystemVersion=13.0`。这只是 Electron 的底线；sharp/libvips、未来独立插件所带 Node、字体、权限及 OS 行为均可能进一步抬高有效要求。sharp 安装文档列 macOS x64 10.15+、macOS ARM64、Windows x64/ARM64；它不构成本项目完整链路的最低系统承诺。独立插件的固定 Node 应单独列系统验收，不能从桌面 Electron 的 13.0 推导它的要求。

每个原生目标至少需要：干净依赖安装及真实 sharp decode；检查安装包内 Electron/原生库的架构；挂载/安装和启动；required 阻断、单实例、托盘/关闭恢复与退出；图片加载与 worker；重启后的 userData 和文件库；升级与卸载保留数据；正式包还需签名、公证/Gatekeeper 或 Windows 签名与安全提示验收。当前单测只证明参数、配置和拒绝门禁，不代替这些实机步骤。
