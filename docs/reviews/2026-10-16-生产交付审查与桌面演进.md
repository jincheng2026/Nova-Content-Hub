### 1.2 习惯性接受、尚未验证的假设

| 假设                                     | 为什么尚不能当事实                                  | 最小验证                                                  |
|------------------------------------------|-----------------------------------------------------|-----------------------------------------------------------|
| “拆出模板后，换标题仍然像，换比例也能用” | 允许任意比例只是一项交互选择；没有质量样本          | 一套模板，三个差异明显的真实标题，目标比例逐一人工验收    |
| “选定的成品最适合当下次参考”             | 交付选择和模型参考是两种意图；旧文字/人脸可能被带回 | 出图前展示可移除清单，固定当次引用，比较带/不带参考的结果 |
| “能唤起宿主，就能可靠交单与回传”         | `opened/filled` 不代表用户发送、AI 接单或成功落库   | 一个宿主真实往返，关联 requestId、taskId 与产物           |
| “普通文件夹不用数据库，就没有一致性问题” | 五份 JSON、图片和任务记录仍可能写一半               | 并发改动、强制退出、失败重试、损坏文件恢复实验            |
| “原子改名 + .bak 已经解决整个事务”       | 只能保护一次文件替换，不能把多份记录一起提交        | 在产物导入、批次登记、任务完成之间分别中断                |
| “硬链接等于独立原图备份”                 | 共享文件内容可能相互影响；跨盘也有约束              | 首版独立复制并核 hash，证明需要后再优化存储               |
| “五个页面都能点，就接近可卖”             | 安装、真实执行、备份、恢复、升级尚无证据            | 干净用户环境完成一次使用，再更新应用并重开原库            |
| “按钮自检通过，就没有 UI 问题”           | 检查器覆盖按钮表面，且存在点错弹层的具体缺陷        | 使用明确动作定位，加业务结果、布局、焦点及键盘断言        |
| “照旅游工程全搬最快”                     | 它有文章、知识库、鉴权等自媒体一期不需要的能力      | 只提取本次竖切用到的模块，记录依赖和移植检查              |

### 1.3 真正想实现的目标

用户拿到一组喜欢的封面后，能沉淀出可复用风格；下一条内容能够用少量输入得到可选择、可修改、可导出且可找回的封面。用户能判断任务现在做到了哪一步，为什么失败，下一步怎么做。

“生产可交付”在这里至少包含：真实产物、真实保存、失败恢复、可安装运行、可诊断维护，以及明确的使用与数据边界。它不要求一期长出团队
SaaS、模型计费平台或自动发布系统。

衡量价值先记录：完成一张可用封面经过几轮、人工花了多少时间、为什么弃图、重启能否找回。尚无基线，不能宣称节省固定比例或改善流量。

### 1.4 现实资源与约束

- 现有资产：五页原型、图片和演示数据、一期业务规格；旅游工作台的桌面骨架、宿主适配、插件组织方式、锁和备份机制。
- 已有约束：外部宿主实际发送仍由用户操作；一份内容库要方便携带；当前范围以封面为主；规格明确排除正文、数据回收、自动发布、多人协作等。
- 未确认：首发 OS/架构、首批用户类型、对外收费与升级支持、可投入人力、生成费用与质量底线。本文不据此编造预算或时间承诺。
- 工程约束：当前未纳入 Git，多会话同时改同一文件会互相覆盖。实施前保存原型快照、建立版本管理和单一写入负责人。
- 产品边界：纯本地资料管理可以离线；AI 生成若依赖外部宿主与供应商，不能承诺全程离线。交付清楚说明哪些内容会交给宿主；日志默认不收集图片、完整提示词和凭据。

## 2. 原方案中只在修补表面的部分

这里的“表面”是指：能改善某一层，但不能单独关闭生产风险，并非这些改动没有价值。

| 现有做法                         | 已解决什么             | 没解决什么                                           |
|----------------------------------|------------------------|------------------------------------------------------|
| 修白底白字、统一图片组件、修灯箱 | 可读性与查看图片体验   | 文件是否真的保存、输出是否真实                       |
| 增加步骤、进度数字、完成提示     | 演示流程可理解         | AI 是否接单、步骤依据是什么、完成为何被标中断        |
| 增加“检查一下”页面               | 诊断入口设计           | 当前多数结果是写死文字，没有探测证据                 |
| 持续追加规格第 14 节             | 快速同步变更           | 前文仍保留旧范围，执行者可能按不同版本实施           |
| 先细定全部目录名与几十种字段     | 有利于命名统一         | 尚未跑通的流程可能不需要这些文件；跨文件提交仍未定义 |
| 恢复内置基线、设计账号授权       | 面向长期维护和商业化   | 核心产物还不能真实生成、导出和恢复                   |
| 直接装入 Electron 或迁 Vue/React | 得到桌面窗口或组件组织 | 不会自动获得正确业务状态、文件事务或安全 IPC         |

应保留的设计：项目内按尺寸和批次挑图、放大与对比、真实图片比例、模板作为可携带数据、人工记发布、库级示例标记、格式过新只读。它们与目标一致。

## 3. 实现审查：必须修复或补齐

P1 表示阻断可信交付；P2 表示会造成错误行为或缺少必要验证。第 1–2 项是明确的原型能力缺口，不能误称为已存在生产服务的回归
bug。

### 1. [P1 / 生产缺口] 业务修改没有可靠落盘

**是什么：** `app.js:39` 只保存 UI 状态；内容创建在 `:1351` 修改内存。上传在 `:1003` 只登记文件名和大小，模板在 `:1404` 使用临时
blob URL。

**问题与后果：** 新建内容、上传、选图或记发布后刷新，业务修改丢失，却已有“存进 JSON / 原始资料”的提示。隔离模型复现了内容重载消失。

**最小完整修复：** 工作台和 CLI 共享一套内容库写逻辑。文件先导入并验证，再登记相对路径；写入回读确认后显示成功。UI
偏好可留本机，不能替代业务事实。

**验收：** 创建、编辑、导入、记发布后完全退出再启动，事实一致；写失败保留用户输入并说明原因。

### 2. [P1 / 生产缺口] 核心生成、交接、导出仍是模拟

**是什么：** `app.js:107、914–924、1009–1011、1202–1233、1316` 分别用 toast、内存对象或定时器替代宿主、目录、下载、图片复制、生成和排期。

**问题与后果：** 用户看到“填进助手”“已下载”“出好了”，实际没有相应交接或文件。`bad` 也会在 `:1771` 无探测恢复为正常。

**最小完整修复：** 演示与工程数据源明确分开；接入真实宿主、任务与产物登记；主进程执行真实导出/剪贴板/目录打开，依据返回结果反馈。诊断页显示探测时间和失败原因，没查过就显示未知。

**验收：** 导出文件可解码且 hash 与选定产物相同；没有宿主回执不显示执行中；找不到库时不会凭计时自行变正常。

### 3. [P1 / 已证实] 请求还原测试，被显示成测试通过

**是什么：** `app.js:1406` 把 `NT.test` 写成 `restoreTest`，`:655` 将真值展示成“对得上”；`:1262` 选模板主要检查有没有图。

**问题与后果：** 刚导入模板、尚未产出测试图，就得到通过标记；待拆解模板也可能被带入出图。

**最小完整修复：** 分离“要求测试”和“实际验收结果”。保存测试图、目标原图、时间与结论。跳过测试可进入实验使用，但不能显示验证通过；正式可用状态须有对应证据。

**验收：** 新建模板永远不会因勾选选项而通过；待拆解、待确认、已验证三个事实显示不同。

### 4. [P1 / 已证实] 模板页会隐式修改上次访问的内容

**是什么：** `app.js:1318–1322` 在缺少显式目标时使用全局 `S.pid`。

**问题与后果：** 先看内容 A，再进模板页点“使用模板”，会修改 A；首次没有目标时却仍可能提示用上了。

**最小完整修复：** 从模板发起时明确选择已有内容或新建内容，随后进入同一个出图配置流程；禁止从残留导航状态推断写入目标。

**验收：** 无目标不会产生修改；所有提交都能明确指出目标内容 ID。

### 5. [P1 / 已证实] 历史发布封面随当前选图漂移

**是什么：** `data.js:282` 发布只记物料 ID；`app.js:511、584` 展示时读取当前 `usedCand`。

**问题与后果：** 发过 01 后改选 02，历史卡片也变成 02，无法回答当时实际使用哪张。

**最小完整修复：** 人工记发布时固定候选 ID、批次、文件/hash；没有证据的旧发布显示封面未知。未发布计划可以明确选择是否跟随当前选定。

**验收：** 后续选图、改模板、重出都不改变历史已发产物；引用中的产物不能被无提示移除。

### 6. [P2 / 已证实] 非法日期进入业务记录

**是什么：** `app.js:240–248、1042–1043、1341` 只拆数字，没有真实年月日校验。

**问题与后果：** `2026-99-99`、`2026-02-30` 都被接受，记录可能无法在日历中定位。独立模型诊断已复现。

**最小完整修复：** 统一严格解析并校验真实日期及闰年；UI 与写入入口都校验。业务日期和带时区时间戳分别存储。

**验收：** 无效日拒绝；合法闰日接受；录制、计划、实际发布共用同一规则。

### 7. [P2 / 已证实] 内置渠道修改规格后重开失效

**是什么：** `data.js:144–156` 允许修改所有渠道，但只存自定义渠道。

**问题与后果：** 抖音改成方图后重载回竖版，封面需求和完成数跟着改变。隔离诊断同时证明自定义渠道能够保存，是有效对照。

**最小完整修复：** 持久化内置渠道的用户覆盖和新增渠道，按库隔离设置；已有批次保留生成当时规格。

**验收：** 修改默认、重开、切库、恢复默认均符合各自语义；不能污染历史批次。

### 8. [P2 / 已证实] 新建合集无法完成

**是什么：** `app.js:1354` 合集输入没有 `#np`，却调用 `:1347–1352` 的内容创建处理器。

**问题与后果：** 填了合集名仍提示缺标题；仅补输入 ID 又会创建成内容类型。

**最小完整修复：** 明确创建类型，分别校验合集的成员和日期结构；保存后返回真实合集。

**验收：** 空/重名/正常创建，添加和移除成员，重开不丢；合集不凭空拥有自己的封面生成任务。

### 9. [P2 / 已证实] 对比选择跨内容串联

**是什么：** `app.js:1301、1284–1286` 选择键只有物料 ID 和候选号；`:1658` 切换内容不清理它。示例中多个内容复用 `cover-v` 等
ID。

**问题与后果：** A 勾选 01/02 后去 B，B 的同号图片可能自动被勾上，并进入 B 的对比。

**最小完整修复：** 选择状态按项目隔离或切项目清空；候选有稳定 ID；批次展开状态同样按项目区分。若按规格限制同尺寸比较，入口也要执行该规则。

**验收：** 跨项目、跨尺寸、旧批次折叠切换后对比对象始终是用户实际勾选对象。

### 10. [P2 / 已证实] 正常完成被标成中断

**是什么：** `app.js:1228` 完成时写 `tk.state='stop'`，`:335、460` 将 stop 展示为已中断。

**问题与后果：** 用户拿到候选却被提示继续中断任务；后续无法正确处理重试或重复生成。

**最小完整修复：** 至少区分执行中、待用户、成功、失败、用户中断、失联待核实；批次完成不等于质量验收通过。钩子停止事件只能提供会话信号。

**验收：** 真成功有产物，真中断保留已完成候选，断联不猜成功；重复回调不会重复入库。

### 11. [P2 / 已证实] 同名附件删除多项，恢复承诺无依据

**是什么：** `app.js:1003` 允许同名文件；`:1008` 以文件名过滤全部同名项，且没有保存恢复记录。`:1358` 删除内容也只提示成功。

**问题与后果：** 两个目录的 `a.md` 导入后删一行会删两行；用户被告知可以找回，却没有实现恢复路径。

**最小完整修复：** 资产 ID 与显示名分开；同名导入明确处理；实际移入回收区并登记后再更新界面。恢复重名有规则。

**验收：** 删除和恢复只影响目标资产，相关任务/发布引用不会变成无说明的坏链接。

### 12. [P2 / 已证实的验证缺口] 自检点错弹层，而且未验证业务结果

**是什么：** `_audit.html:72` 点第 4 个菜单按钮；`app.js:1637–1640` 第 3 个才是版本，第 4 个是重命名。

**问题与后果：** 检查器将重命名当成版本弹层检查，且 `check()` 不核对标题或业务状态。插入的自检错误也始终留在 bad
列表，不能简单以“无输出”判定产品通过。

**最小完整修复：** 使用稳定动作标记定位，断言正确标题与状态，把检测器自测与产品问题分开。保留外观烟测，另做少量真实业务端到端验证。

**验收：** 故意破坏一个动作应令相应断言失败；能验证新建合集、产物导出、重启保留等具体结果。

## 4. 应一并解决的工程与体验问题

### 13. [P2 / 信任边界缺口] 发布链接只有 HTML 转义，没有协议校验

`app.js:1045、519` 接受链接并直接用于 `href`。HTML 转义不能阻止 `javascript:` 等非预期协议。当前 HTML 没有
CSP，图片和部分节点还使用内联事件。

最小修复：保存时和打开时解析 URL，只接受明确允许的 HTTP (S)；拒绝内嵌脚本协议。迁 Electron
时使用安全外链入口，原始导入文本只作文本显示；删除内联事件以配合严格脚本策略。此项已由源码确认缺少校验，
**没有执行注入，也没有宣称当前发生桌面代码执行**。

跳过的风险：导入/粘贴的内容能扩大执行面；一旦桥接具有本地权限，后果更重。验收应包括危险协议、畸形 URL、路径越界、符号链接越界以及非主窗口
IPC。

### 14. [P2 / 模型不一致] 比例、像素、规格混在一起

`data.js:82、91` 横版定义为 16:9，同一数据的说明却写 B 站 16:10；`:97–101` 只做字符串匹配，所以 1080:1440 和 3:4
被当不同规格。后者隔离诊断已复现； **本文未复核平台尺寸标准，不替这两组数字背书**。

最小修复：区分风格、目标比例、目标像素、产物实际像素、渠道建议；等价比例规范化。渠道建议有来源和核查状态，未核查不能显示已核实。用户选定不锁任意比例时，仍保留每次产物的真实尺寸与验收记录。

跳过的风险：相同需求被重复出图、完成数不准确，或文件不能满足发布目标。验收用 3:4/1080:1440 等价、零值、过大值、不同实际像素及不符规格输出。

### 15. [P2 / 静态布局问题，待渲染复核] 窄窗口轨道与图片宽度不一致

`styles.css:330` 窄窗口首列变为 76px，但 `:150` 缩略图仍固定 96px；加上 14px
间距仍会伸入下一列。截图也有封面挤压标题的线索，但未做当前浏览器复现，不能把全部遮挡都归因于这一处。

最小修复：缩略图宽度随轨道变化；列表与合集明确各自列结构；给标题保留可读空间，空间不足切卡片。`app.js:398–406`
合集表头、行和通用八列布局也须一起核对。

跳过的风险：桌面分屏和缩放下列表难读。验收固定窄/标准窗口、长中文标题、125%/150% 缩放、空图及多状态标签，测文字/图片相交与水平溢出。

### 16. [P2 / 可访问性缺口] 多个操作入口仅支持指针

`app.js:375、389–406、1658` 的内容/合集主要通过 div 点击进入；`:108–118` 弹窗没有对话框语义、焦点进入与返回管理。图标按钮多只依赖自定义提示。样式检查器不能证明键盘可用。

最小修复：可操作元素用 button/link，提供可访问名称；弹窗管理初始焦点、Tab 范围与关闭后焦点；不让后台页面抢键。无需引入大 UI
框架。

跳过的风险：键盘用户、辅助技术和桌面高频操作无法可靠使用。验收用纯键盘走新建→出图配置→候选选择→导出，关闭弹窗回到原触发点。

## 6. 从事实重新推导的路径

### 6.1 先借现有桌面能力，验证一条真实业务链

推荐顺序： **冻结当前设计 → 选择性复用旅游桌面骨架 → 一条真实链路 → 数据故障验收 → 补齐五页真实能力 → 桌面安装升级验收**。

不把 Electron 留到页面全写完以后。真实文件选择、图片导出、宿主唤起本就是桌面需求，现在就借已有骨架验证；也不复制旅游整套产品后大规模删除。

| 可复用候选                            | 已检查的参考源码                        | 移植时必须确认                                          |
|---------------------------------------|-----------------------------------------|---------------------------------------------------------|
| Electron/Vue/TS、构建、测试与打包组织 | 参考工程 `workbench/package.json`       | 只保留本期依赖；应用 ID、用户目录、图标、资源目录独立   |
| 有限 preload 业务方法                 | `workbench/src/preload/index.ts:1`      | 内容动作独立定义，不搬文章/知识库/旅游卡字段            |
| 宿主发现与跳转 URL                    | `src/main/codex.ts:1`、`workbuddy.ts:1` | 新插件 ID、Skill 名、库路径及宿主版本的真实行为         |
| 读写通道分类与过新库只读              | `src/main/read-only.ts:1`               | 所有 IPC/CLI/后台清理都受约束，新增通道不能漏归类       |
| 文件锁、临时写、回读和备份恢复        | `plugin-src/src/lib/fsx.mjs:1`          | 与旅游 layout/output 耦合需解开；锁键和恢复策略适配新库 |
| 桌面与 CLI 共用业务逻辑的接法         | `src/main/library/plugin-lib.ts:1`      | 自媒体路径与结构由自媒体拥有；不能两边各抄一份算法      |

首版不抽跨行业平台。只有两个业务实际验证出相同稳定行为后，再决定共享包范围。复用具体机制，而不是提前制造几十个“通用扩展点”。

### 6.2 数据只保留必要的事实

| 对象      | 最小必要事实                                          | 不应混入                   |
|-----------|-------------------------------------------------------|----------------------------|
| 内容      | 稳定 ID、标题、渠道、素材引用、计划                   | UI 筛选和页面是否展开      |
| 模板版本  | 原图证据、生成约束、版本、实际测试结论                | 用户勾选意愿冒充通过       |
| 执行任务  | 关联请求、目标内容、输入快照、状态、错误、产物引用    | 由时间推算的假进度         |
| 批次/候选 | 稳定 ID、真实文件、尺寸、hash、生成来源、所用模板快照 | 仅靠可重复编号定位对象     |
| 选定      | 每个目标规格当前候选引用                              | 覆盖已发布历史             |
| 发布记录  | 人工声明、实际日期、渠道、可选链接、固定产物引用      | 未接平台数据却声称平台确认 |

初始文件夹布局可沿用规格的简洁方向，但内容卡、待办已退出当前范围，不必为它们先造空 JSON。文件布局由 `layout`
一处定义，业务校验由内容模块掌握，缓存可删可重建。是否引入 SQLite 应由查询、并发和迁移实测决定，不能把“永远不用数据库”当基本事实。

### 6.3 写入和产物提交必须完整

单条写：校验目标及参数 → 检查库版本/只读 → 获取一致的锁 → 重读最新数据 → 检查版本并合并本次修改 → 写临时文件并刷盘 →
保留上一份有效数据 → 替换 → 回读确认 → 释放锁。

跨图片/批次/任务提交：先将产物复制到本任务暂存区 → 解码并验证真实格式、尺寸与 hash → 移入受管理资产位置 →
原子提交批次清单 → 将任务关联到已提交批次。操作有稳定 ID；重复提交返回已有结果，不能再追加一批。用最小操作记录支持中断恢复。

不能把五个文件的 rename 称作一个事务。进程在任一步退出，重开要能辨识：已提交产物、未提交暂存、待核实任务；恢复不能覆盖用户之后的修改。锁超时不能凭时间随意抢占仍存活的写入者。

外部宿主具有它自己已获授的文件权限。工作台的 Electron 沙箱约束不了另开的宿主；插件统一通过 CLI
写入是需要测试和规范约束的协作规则，不能宣传成操作系统强制隔离。

## 7. Electron 具体落点

```text
界面 renderer：视图、输入、候选比较、用户确认
        ↓ 有限业务动作与结构化结果
preload：只暴露命名动作，不暴露通用 fs / shell / IPC
        ↓
main：选库、导入、导出、剪贴板、宿主交接、内容库读写
        ↓ 共享内容模块
CLI / Skills：同样的校验、路径、锁、任务与产物提交
        ↓
用户选定的内容库 + 用户目录内可重建缓存/本机偏好
```

Electron 官方建议启用隔离、进程沙箱和 CSP，限制导航/新窗口，验证 IPC 来源，谨慎处理外链。生产实现依这些建议设置权限，使用库内资源协议并校验实际路径；不接受
renderer 提供任意文件路径或命令。[安全建议](https://www.electronjs.org/docs/latest/tutorial/security)

preload 每个方法对应有限业务能力，例如选择内容库、导入素材、选择候选、导出封面；主进程重新校验参数，结构化返回成功、取消、冲突或失败。官方示例采用
`invoke/handle` 请求响应，并明确不暴露整个 IPC 调用能力。[IPC 文档](https://www.electronjs.org/docs/latest/tutorial/ipc)

宿主侧复用现有适配器，结果区分未安装、仅打开、已预填、待用户发送、已接单、执行失败。首版允许“真实复制完整指令并手动粘贴”作为降级，不能把降级说成自动填入；冷启动和超长指令单独测试。一个宿主通过后再接第二个。

打包资源、示例库、生产库分离；升级不覆盖用户库。示例首次复制到可写位置，格式随应用一起验证。macOS 对外分发需规划签名和公证；Windows
按分发渠道验证签名与安装体验。[代码签名文档](https://www.electronjs.org/docs/latest/tutorial/code-signing)

自动更新是独立交付能力，macOS/Windows
元数据有差异。首批可先用可验证的手动更新；无论是否自动，必须验收新旧应用与库/插件版本不匹配时的行为。[应用更新文档](https://www.electronjs.org/docs/latest/tutorial/updates)

## 10. 这条路径成立的前提

1. 首版确实接受单人单机和本地库；若需要团队同步，需要重新设计冲突、权限及同步协议。
2. 用户愿意使用指定外部宿主并手动发送；至少一个宿主能真实执行内容 Skill 并可靠回写。若要求一键无宿主，模型
   API、凭据、计费和任务执行将成为新的产品范围。
3. 真实模板在不同标题下可产出可接受结果；允许重试、人工选择和明确的费用提示，不能保证每张一次成功。
4. 桌面和插件使用同一套结构/校验/锁/提交协议；人工直接改文件时程序能检测损坏并安全降级。
5. 有目标系统上的实际测试环境，以及对外分发所需签名/公证和支持安排；不能用开发机启动代替用户安装验收。
6. 不把参考工程中的代码存在、注释中的历史实测、或当前原型成功提示当作新产品已经验证的证据。

## 11. 验证它的第一步

**开一个范围很窄的真实竖切实验：一个宿主、一套模板、一条内容、一个目标规格。借已有桌面骨架完成导入 → 宿主接单 → 产物登记 →
人工选定 → 文件导出 → 完全退出重开。**

实验只用独立测试库，不动真实资料库。先跑通单标题链路，再用三个不同标题检验模板复用。自动跳转未成功时采用明确的手动交接，不伪造接单。

记录五类证据：输入与模板版本、宿主任务关联、真实产物及 hash/像素、人工选择和拒绝理由、重启后的库内容。追加两个故障：在结果登记中途退出；重复提交同一结果。

成功标准：导出与选定文件一致；重开仍在；失败可解释并保留已有成果；重复不会多一批；没有接单不展示运行。模板测试至少得到能指出具体好坏的真实样本，而非先承诺任意比例质量。

如果宿主不能稳定回写，先修交接/回传；如果模板换标题无法保持质量，先修拆解和生成约束；如果重开丢数据，先修写入恢复。任何一个失败，都不该用更多页面掩盖。
