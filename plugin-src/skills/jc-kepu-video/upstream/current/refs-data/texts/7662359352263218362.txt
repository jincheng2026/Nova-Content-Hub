看懂这六个术语，你就能够看懂大多数的 Agent 系统是怎么搭起来的。分别是 AGENTS.md、Skill、MCP、Memory、A2A，以及 Subagent。

很多人都会以为，Agent 和 Agent 的差距是模型有多聪明。但其实模型只是一个脑子，你可以把它想象成一个聪明的新人。脑子再好，第一天来上班也得知道规矩，要配齐工具，要配齐权限，要记住相关背景，这样才能真的把活给干完。

所以我们先直接从第一样开始，AGENTS.md。AGENTS.md 本质上是一个给 Agent 看的说明书，所以它是一个文档。有很多人会觉得，这个 .md 是后缀，我好像都没有见过，对吧？一般都是 .doc、.ppt。其实 .md 也是一个普通的文本文件。你把它放在你的项目根目录，Agent 一进来开工，它会先去读它。

这个文档里面会写什么呢？第一，这个项目怎么启动，测试跑哪条命令，代码风格是什么，哪些文件不能动，提交信息怎么写。你就把它理解成贴在新人电脑旁边的那本项目须知就行了。新人再聪明，第一天来也不知道你这儿怎么干活。你不告诉他规矩，他只能靠猜。很多人抱怨 Agent 笨，其实不是他笨，是你压根就没告诉他这个项目是怎么运转的。

另外，AGENTS.md 还可以分层。你可以在根目录放一个总的规则，然后各个子目录放子规则。如果某个目录的规则不一样，那你就在这个子目录里面再放一份，离任务最近的那份会最优先读取。所以总部有总部的规矩，进入了分部，你就得听分部的。这个 AGENTS.md，我觉得是成本最低、回报最高的一样东西，如果你把它完善好的话。

好，第二个词叫做 Skill。Skill 解决的不是规矩问题，而是手艺的问题。有些能力，Agent 不是天天都要用，比如做 PPT、处理表格、写特定格式的报告、生成某种固定风格的图片。如果你把这些东西全部塞进它的上下文里面，那它今天明明只是改了一段文案，也要背一整套 PPT 怎么制作的手册去干活，脑子就被占满了。

所以 Skill 的思路很简单：不用的时候，我把它放在一边、挂在墙上；用的时候，我再把它拿下来。一个 Skill 通常就是一个文件夹，里面有一个 SKILL.md，告诉 Agent 我这个是什么技能、什么时候该调用；旁边还可以放脚本、放模板、放素材。

所以 Skill 不是装得越多越强，真正关键的是，该用的时候再加载，不该用的时候千万别打扰。我见过太多人把几十个技能一股脑全部挂上，以为这样 Agent 就会更强，结果反而更笨，因为它每次都要在一堆用不上的东西上面做判断。所以 Skill 你应该理解为一个工具墙，而不是一个杂物堆。

好，第三个词，我们讲 Memory。这个我觉得是最被低估的一块。上下文窗口只是 Agent 当下的工作台，你这一轮给它什么，它就临时看什么，但对话一关，很多东西就没掉了。Memory 解决的是另一个问题：它明天还记不记得你？所以它是一个记忆。

你想象一个同事，每天早上一进门都不认识你，不知道你在做什么项目，不记得昨天定过什么事，你每次都得从头解释。那这种同事再聪明，没有记忆也很难长期协作。所以一个真正好用的 Agent，一定不只是当下会回答，它还要慢慢记住你的偏好、项目背景、工作方式，以及哪些规则被验证过了、哪些事情不要再重复。

但 Memory 最难的地方不是记住，最难的是哪些该忘的，你就得给我忘掉。你看，什么都往里面塞，理论上这个 Memory 的窗口再大，它也会被填满。时间长了，记忆里全都是一些过期的信息、错误判断、互相打架的规则，Agent 会越用越糊涂。所以好的 Memory 不是记得越多越好，而是记得准、更新得动，也删得掉。这个非常重要。

AGENTS.md、Skill 和 Memory，更多是在解决 Agent 自己身上的问题。接下来讲的三个，解决的是它怎么跟外部世界打交道。

第四个词叫做 MCP。MCP 你可以理解成一个统一的插座。Agent 真正干活不能只在聊天框里面说，它得查数据库、读文件、连 Notion、调接口、操作各种工具。但问题是，每个工具的接口都不一样。过去你想接一个工具，就得专门给它做一个适配；接十个工具，就得接十套适配；做一百个，就得接一百个。这样的话就真的一团乱。

所以 MCP 做的事情，就是把这些接口统一起来。工具那边提供一个 MCP Server，Agent 只要会说 MCP 这种话，就能通过它调用这样的外部工具。所以 MCP 最大的意义，是让 Agent 从动嘴变成了动手。以前它只能告诉你这件事应该怎么做，有了 MCP，它就真的可以去做，可以去改，可以去提交，可以去调用。

当然，这也有风险。你给 Agent 接这些工具，本质上是在给它发钥匙。能查数据库、能改文件、能发消息、能操作线上系统，钥匙越多，能力越强，但是风险也越大。所以 MCP 很重要，但权限、安全、确认机制也必须一起考虑。

好，第五个词，A2A。MCP 管的是 Agent 和工具怎么连接，A2A 管的就是 Agent 和 Agent 怎么连接、怎么协作。比如一条内容生产流水线，一个 Agent 负责找选题，一个 Agent 负责写稿，一个 Agent 负责配图，一个 Agent 负责检查发布格式。他们之间怎么知道彼此干什么？任务怎么交接？结果怎么返回？A2A 解决的就是这个问题。

你可以把它理解成 Agent 之间互相递名片。每个 Agent 亮出一个 Agent Card，告诉别人：我是谁，我能干什么，你该怎么把任务交给我。所以你看，MCP 是对工具的，A2A 是 Agent 对 Agent，千万别把 MCP 和 A2A 搞混了。

但这里我也说个实话，多 Agent 协作这件事，我觉得现在还是被高估了。很多看起来很酷的多 Agent 演示，一个 Agent 配齐工具也能更稳、更便宜地完成。所以多 Agent 不是越多越高级，只有当任务真的拆得开、角色真的不一样、流程真的需要交接，才值得上 A2A。否则你只是把一个简单问题，变成一个需要协调一群 Agent 的复杂问题。

好，最后一个词叫做 Subagent。Subagent 你可以理解为子 Agent，也可以理解为分身。它适合两种情况：一种是任务太大了，一种是上下文装不下。

比如你让 Agent 读几百集的剧本，主 Agent 不可能把所有内容都塞进自己脑子里面。这样的话，它可能就派一个子 Agent 去读，只要让这个子 Agent 回来总结完，给我递交人物关系和时间线概要就可以了。

另一种就是任务可以并行。比如同一篇文章要改成八个平台版本，我用一个 Agent 一个一个改，非常慢。这个时候，你可以构建八个子 Agent 同时做，这样就会快非常多。

所以主 Agent 不需要亲自做完所有细节，它更像一个主管，把任务拆出去，再把结果回收回来。而 Subagent 最爽的地方，就是速度真能上来。但它也最容易被滥用，不是所有的事情都值得拆。任务太轻了，最后光协调、合并、检查就要比原来更麻烦。所以 Subagent 解决的是两个问题：装不下，或者等不起，真的不是用来炫技的。

好，六个讲完，我们再回头看一眼。AGENTS.md 是立规矩，Skill 是讲手艺，Memory 是讲记忆，MCP 是工具调用，A2A 是 Agent 和 Agent 之间的协作，Subagent 是分身和并行。这六样东西拼起来，才是一个真正能干活的 Agent 系统。

所以我越来越觉得，Agent 的差距不只是模型排行榜上的差距。模型当然重要，它决定这个脑子聪明还是不聪明。但真正让它从会聊天变成能交付的，是模型外面那套系统：规矩有没有写清楚，技能是不是按需调用，记忆是不是可靠，工具能不能接，协作有没有必要，任务能不能拆得动。这些东西才决定一个 Agent 到底只是看起来厉害，还是真的能够把这些活给干完。

所以如果你现在想给自己搭一个 Agent，别上来就纠结模型了。你先问自己一个更实际的问题：这六样里面，我到底缺的是哪一样？
