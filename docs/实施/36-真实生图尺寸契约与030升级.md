# 真实生图尺寸契约与0.3.0升级

2026-10-18。安装版真实验收发现的核心可用性问题，不是靠修改旧回执或复用历史图片修补。

## 原路径为何失败

安装版界面只让用户选择比例，却自动创建精确900×1200请求。实际Codex独立生成两张1086×1448 PNG，恰好3:4，原图清晰且未修改；核心仍按精确像素正确拒绝。两张原字节、固定请求、失败状态和零候选均保留，[原始证据](../verification/production/2026-10-18-unified-codex-size-failure-01.json)。没有裁切、拉伸、改hash或把这批失败产物移交新请求。

工作台已真实请求系统打开Codex，但CUA拒绝操作Codex窗口。后续使用用户已授权的临时验收会话、官方会话接口执行同一handoff ID；因此这次有真实宿主读图、生图和提交证据，**没有当前Codex原生预填/发送界面验收**。临时会话ID为`01a14f99-dcbc-72e2-81f0-967c9eb7177b`。不将它写成完整图形桥接通过。

## 从用户目的重新约束

普通封面需要正确比例、足够清晰的真实原图和一组可挑选候选；界面没有收集过“必须精确900×1200”的要求。新普通请求使用`sizePolicy: ratio-minimum`，pixels代表最低显示尺寸；输出保留原始字节，比例须整数交叉乘完全一致，两维均不得低于最低值。最低短边768，比例约分后取整数倍：3:4为768×1024，1:1为768×768，16:9为1376×774；最大40MP、格式、数量、重复图、单张/整批大小及原子登记限制保留。这是产品最低线，不保证任意工具或自定义比例必定能生成。

旧输入省略策略或明确exact时保持原归一化和v1请求，继续精确验收；新ratio-minimum进入inputHash/requestHash并使用请求v2。只接受v1无策略/v2有明确ratio-minimum，未知组合拒绝。EXIF显示方向参与判断，不借尺寸规则改变原图。库仍为schema5，handoff/receipt执行协议仍为v1；旧v1-only读取器拒绝执行v2，不宣称旧版本完整支持新任务。

桌面IPC、pending恢复、重试、换宿主和历史摘要透传策略；界面写“至少…，实际尺寸以生成结果为准”。执行Skill按writing-for-agents规范同步两种策略，要求真实生成及完整校验回执，不把宿主会话结束当成功。

## 版本升级

本轮真实观察到官方安装器复用同版本0.2.0缓存，更新报告成功但执行文件未替换。因此产品、桌面、插件统一升0.3.0，不原地发行另一个0.2.0。根release、两package/lock及新备份toolVersion同步；生成配置、manifest、integrity和市场由构建派生。历史资料、旧请求、原备份及第三方依赖的0.2.0保持不变。

0.3.0桌面拒绝只有0.2.0缓存的助手；旧handoff绑定旧pairId，新插件应拒绝。桌面继续入口可给旧固定请求生成新定位envelope，不能改请求原字节。升级后仍要通过官方安装确认新Skill路径，readiness不能替代宿主真正加载新版。
